# 滚动截图诊断：B1 真机实测的两处异常

来源：一次 Notepad3 长文档（30 000 行 txt）的 release 版滚动截图。原始读数：

```
[snapclip][scroll] image 1250x80882: working 4.0 MB (80882 rows), temp 400.4 MB
[snapclip][scroll] stopped frames=11344 read_mean_us=1828 ... push_us: p50=599 p95=1268 max=5060
[snapclip][bench] stage=export size=1250x80882 encode_write_ms=4586
[snapclip][scroll] clipboard copy done ms=220
```

外部采样（每 0.5 s，`snapclip-app.exe` 工作集）：基线 93.5 MB → 峰值 **152.7 MB**（t≈124 s）→ 结束时仍 149.5 MB，**采集进行中持续上升**，180 s 内 +59.2 MB。

本文只做诊断，**未改任何产品行为**。

---

## 一、先说结论

| # | 问题 | 结论 | 强度 |
| --- | --- | --- | --- |
| 1 | +59 MB 去了哪 | 增速与**帧数**同步，与**行数**无关 ⇒ 在**每帧路径**上，不在拼接器（拼接器 4.0 MB 是日志实测） | [实测] 相关性 / [推断] 归属 |
| 2 | 7 行/帧 是缺陷吗 | **不是"每帧只滚 7 行"**，而是"**每帧净增长 7 行，而采样到的位移是 93 行**" ⇒ 二者差 13 倍，说明**大多数帧没有转成画布增长** | [实测] 算术 / [待测] 成因 |
| 3 | 与 Notepad3 平滑滚动有关吗 | **不是主因**。平滑滚动会让每帧位移变小，但**不会**让"位移 93"与"增长 7"同时成立 | [推断]（已排除为主因） |

最关键的一条是 **#2 的算术矛盾**，它不是 UX 问题，而是**拼接质量的风险信号**，值得优先查清。

> **B2 已收口（仪器运行，见 §八）**：内容无损（账目分毫不差 ✓）、"7 行/帧"是 86% 的静止帧造成的"慢但正确" ✓、+59 MB 是被启动期放大的假象，真实增长约 **+1.2 KB/帧** ✓。以下 §二/§三 的原始推断保留作过程记录，结论以 §八 为准 ✓。

## 二、问题一：+59 MB

### 已知数据

| 观测 | 值 | 来源 |
| --- | --- | --- |
| 拼接器自身工作内存 | **4.0 MB**（80 882 行） | [实测] 会话结束日志 |
| 进程工作集增量 | **+59.2 MB** | [实测] 外部采样 |
| 采集帧数 | **11 344** | [实测] `stopped frames=` |
| 每帧增量 | **≈5.2 KB/帧**（59.2 MB ÷ 11 344） | [实测] 算术 |

### 相关性判据（这是本次能拿出的最强证据）

对比三次真机运行：

| 运行 | 帧数 | 行数 | 工作集增量 |
| --- | ---: | ---: | ---: |
| 25 857 行那次 | 1 346 | 25 857 | +9.2 MB |
| 38 815 行那次 | 4 335 | 38 815 | +7.2 MB |
| **B1（80 882 行）** | **11 344** | 80 882 | **+59.2 MB** |

- 增量与**行数**不同步：行数 25 857 → 80 882（×3.1），增量 9.2 → 59.2（×6.4）；中间那次行数涨了 50% 而增量**下降** ✗；
- 增量与**帧数**同步：1 346 → 11 344（×8.4），增量 9.2 → 59.2（×6.4）✓。

⇒ **结论**：增长挂在**每帧**的处理路径上，而不是"存了多少行"。拼接器（tile / 环 / 目录）已被排除 —— 它在 80 882 行时仍只占 4.0 MB [实测]。

### 候选清单（按可疑程度）

| 候选 | 位置 | 每帧量级 | 判断 |
| --- | --- | --- | --- |
| `total_us` / `read_us_all` 两个 `Vec<u64>` | `windows/scroll_worker.rs:308-309` | 16 B/帧 ⇒ 总 181 KB | [实测] 数量级不符，**排除** |
| WGC 帧池 / staging 纹理 | `windows/win/wgc.rs`、`read_region` | 每帧一次读回 + 纹理 | [推断] 可能，但池通常有上限 |
| 逐帧 dirty rect 列表 | `CaptureOptions.dirty_regions: true` | 未知 | [推断] 可能 |
| 缩略图 scratch / 预览回收缓冲 | `recycled: Mutex<Vec<u8>>` | 单缓冲 | [实测] 单缓冲，**排除** |
| 每帧日志字符串 | 已节流（每 60 帧） | 可忽略 | [实测] **排除** |

**无法从代码单独定论** —— 需要在进程内取数（见下文"要加的仪器"）。

## 三、问题二：7 行/帧 还是 93 行/帧

### 算术

```
采集行数 80 882 ÷ 帧数 11 344 = 7.13 行/帧（净增长）
日志里所有被记录的帧：dy = 93（21 个样本，全部是 93）
                                                    ↑ 两者差 13 倍
```

`log.txt` 中 B1 附近的 `dy` 采样**只有 93**（`grep -o "dy: -[0-9]*"` 得到 21 次、全是 93）——但日志是**节流后**的（首帧/状态变化/每 60 帧），所以它只代表"被记录的那 21 帧"。

**两条推论不能同时成立**：

1. 若**每帧**都 `Shift dy=93` 且被 append，11 344 帧应产生 ≈105 万行 ⇒ 早在第 ~870 帧就撞上限 ⇒ 与"上限在最后才出现（`status=Full` 只出现 1 次）"矛盾 ✗；
2. 若**大多数帧**是 `Contained` / `Unknown`，则净增长 7 行/帧 ✓ 与观测一致 ⇒ **被采样的 21 帧恰好都是 `Shift`**（节流规则让状态变化优先被记录 ⇒ **采样偏差**）✓。

⇒ **结论**：7 行/帧 **不是"每帧只滚 7 行"**，而是"**每帧净增长 7 行，而部分帧的位移是 93**" ⇒ 中间有大量帧**没有变成画布增长**。

### 为什么这不是 Notepad3 平滑滚动

平滑滚动会让每帧位移**变小**（例如 93 被拆成 13 帧 × 7），那时日志里的 `dy` 应该**大量出现 7** ✓；而实际日志里 `dy` **只有 93** ✗。所以平滑滚动解释不了"位移 93 与增长 7 并存" ⇒ **已排除为主因** [推断，依据为采样偏差说明] ✗。

### 真正的待测项：**放置分布**

需要的是**每一帧的 placement 统计**（`Appended` / `Prepended` / `Contained` / `Full` / `Unknown` 各多少帧）✗ —— 现有日志只有节流样本 ✗。这一个直方图就能回答：

- `Contained` 占多数 ⇒ 位移估计把"页面在动"判成"内容已在画布内" ⇒ **拼接会丢内容** ✗（严重）；
- `Unknown` 占多数 ⇒ 估计不可靠（Notepad3 的文本渲染/光标闪烁）⇒ 丢帧 ⇒ 图像**跳段** ✗；
- `Full` 占多数 ⇒ 单纯撞上限 ⇒ **无问题** ✓（只是截不完）。

## 七、仪器（已实现，`test-support` 门控）

两件都只存在于测量构建里，产品构建中**一行代码都没有**。

### 7.1 放置直方图（`scroll::stats`）

每帧记一笔，会话结束时打印一行：

```
[snapclip][scroll] placements: appended=N contained=N prepended=N unknown=N full=N moved_px=SUM nonzero=N frames=N
```

- `moved_px` 是 `|dy|` 的累计，`nonzero` 是有位移的帧数 —— 这两个数直接回答"到底移动了多少像素"，而不是依赖节流日志里的样本；
- `unknown` 不是 `Placement` 变体（估计失败时 `placement = None`），所以在 worker 里与 `Placement` 一并统计；
- 纯结构 + 纯函数，单测覆盖：五种放置各归各的计数、负位移按距离累计、以及"一段很长的静止帧"必须与"每帧都在动"在计数上明显不同。

### 7.2 进程内工作集（`windows::proc_mem`）

每 **1000 帧**打印一行：

```
[snapclip][scroll] mem: frame=N ws=X.X MB timings=N reads=N rows=N
```

- `ws` 取自 `K32GetProcessMemoryInfo`（`-1` 伪句柄，无需打开/关闭进程）—— FFI 在本文件内声明，**不**扩大 `windows-sys` 的特性集（那是 crate 级的 ✗）；
- `timings` / `reads` 是两个逐帧样本向量的长度（每帧 8 字节 ✗ 太小，不足以解释 5 KB/帧），`rows` 是画布行数 ✓；
- 单测断言返回值"在本进程上合理"（> 1 MiB 且 < 1 TiB）—— **结构体布局写错也会返回一个数** ✗，所以必须用一个量级检查兜住。

### 7.3 零影响的证明（以及上一版证明方法的错误）

**正确的证明在 debug rlib 上做**（`[profile.release]` 是 `lto = true` + `strip = true` ⇒ release rlib 里是 bitcode，**字符串字面量根本不在里面** ✗）：

| 构建 | `placements: appended` | `mem: frame=` | `K32GetProcessMemoryInfo` | `SEAL_FAULT_AT` |
| --- | ---: | ---: | ---: | ---: |
| 默认 | **0** | **0** | **0** | 0 |
| `--features test-support` | **1** | **1** | **2** | 0 |
| `--features seal-faults` | 0 | 0 | 0 | **1** |

每种仪器只出现在带它自己特性的构建里 ✓，默认构建三项全 0 ✓。

> **更正**：`docs/35 §19` 里"默认 release rlib 搜 `SEAL_FAULT_AT` = 0，带特性 = 2"这条证据**不成立** ✗ —— 在 `lto = true` 下 release rlib 是 bitcode，字面量不在其中；那里的 0 与 2 都不能说明门控。改用本节的 debug rlib 方法后，`seal-faults` 的门控才真正被证明（表中 `SEAL_FAULT_AT` 只在 `seal-faults` 构建里出现 ✓）。

### 8.2 结论一：内容没有丢，账分毫不差 ✓ [实测]

四条等式全部**精确成立**（不是"接近"）：

| 等式 | 左 | 右 | 判定 |
| --- | ---: | ---: | --- |
| 画布行数 = 首帧视口 + 追加总和 | 809 + 861 × 93 = **80 882** | 画布 **80 882** | ✓ 完全相等 |
| 位移总和 = 追加位移 + 撞上限后位移 | 80 073 + 455 × 93 = **122 388** | `moved_px` **122 388** | ✓ 完全相等 |
| 有位移的帧 = 追加帧 + 撞上限帧 | 861 + 455 = **1 316** | `nonzero` **1 316** | ✓ 完全相等 |
| 帧数 = 追加 + 撞上限 + 未知 | 861 + 455 + 8 368 = **9 684** | `frames` **9 684** | ✓ 完全相等 |

⇒ **每一个像素、每一帧都有归属** ✓ —— 不存在"位移消失却未记账"的路径 ✓。
撞上限之后仍在统计的那 42 315 px 被 `full` 精确吸收 ✓，这正是它该有的行为 ✓。

与用户目视结论（**无重复、无缺失横带** ✓）互相印证 ✓ —— 代码侧的账与肉眼看到的图一致 ✓。

### 8.3 结论二："7 行/帧"其实是"86% 的帧是静止帧" ✓ [实测]

| 量 | 值 | 占比 |
| --- | ---: | ---: |
| `unknown`（估计失败：页面没在动） | **8 368** | **86.4%** |
| `appended`（真正推进内容） | 861 | 8.9% |
| `full`（撞上限后） | 455 | 4.7% |
| `contained` / `prepended` | 0 / 0 | — |

- 9 684 帧 ÷ 861 次推进 ≈ **11.2 帧/次** [换算]；
- 即自动滚动**每次要等约 10 帧**（≈0.3 s）确认"画面静止"才走下一步 ✓；
- 所以"7 行/帧"只是**平均值**的错觉 ✓ —— 真正推进时每次都是 **93 行** ✓，其余时间页面根本没动 ✓。

加速杠杆**不是**"等静止"的帧数 ✗（那个旋钮不存在 ✓，见第十节），而是 notch 间隔 `AUTO_INTERVAL` ✓ —— 已实测三档并改为 **60 ms** ✓（见第十节）。

### 8.4 结论三：+59 MB 是被启动期放大的 ✗ → 真实增长约 +1.2 KB/帧 ✓ [实测]

- 进程内：第 1 000 帧 **129.4 MB** → 第 9 000 帧 **139.1 MB** ⇒ **+9.7 MB / 8 000 帧 ≈ 1.2 KB/帧** [换算]；
- 两个逐帧样本向量（`timings`/`reads`）每千帧各 +1 000 条 × 16 B ⇒ **32 KB/千帧** [换算]，8 000 帧合计约 0.26 MB ⇒ **数量级不符，排除** ✓；
- 外部采样得到的 93.5 → 152.7 MB（**+59.2 MB**）**混进了应用启动期的 GPU/UI 初始化** ✗ —— 那次采样的基线取自进程刚启动时 ✓。

⇒ **以进程内测量为准** ✓；采集/渲染侧约 **1.2 KB/帧** 的温和增长单独立项 ✗（不急 ✓）。

### 8.7 剪贴板的瞬时峰值（外部采样抓到的、唯一的大数）✗

同一次外部采样（818 样本 / 420 s）在**导出阶段**抓到一个尖峰，其余时段都很平稳：

| 时段 | 工作集 |
| --- | --- |
| 启动期 0–30 s | 97.8 → 131.9 MB（GPU/UI 初始化 ✓） |
| 采集期 70–175 s | 130.3 → 139.1 MB（与进程内 `mem:` 一致 ✓） |
| **t ≈ 194 s（导出 + 剪贴板）** | **941.3 MB** ✗ |
| 之后 210–419 s | 103–104 MB 平稳 ✓ |

对账：**404 MB（80 882 × 1250 × 4 的连续 DIB）× 2 + 基础约 100 MB ≈ 908 MB** ✓，观测 941 MB ✓。

**公式**：`剪贴板峰值 ≈ 行数 × 宽 × 4 × 2`（一张 DIB + 一份中间副本 ✓）。常见规模：

| 行数 | 峰值量级 |
| ---: | ---: |
| 25 857 | 约 260 MB |
| 38 815 | 约 390 MB |
| 80 882（100 屏上限附近） | **约 810 MB** ✗ |

**这是 Windows 剪贴板要求"连续 DIB"的固有成本** ✓，不是拼接器的 ✓（拼接器全程 4.0 MB ✓），也不是这次改造引入的 ✗ —— 但它在长图上**随行数线性增长** ✗，所以 100 屏时会把进程推到 ~1 GB 的瞬时峰值 ✓。

**三个可选处置（均未实现 ✗）**：

1. **不动** ✓ —— 瞬时（约 0.2 s）、随即回落、64 位进程不会失败 ✓；代价是低内存机器/pagefile 会难受 ✗；
2. **超大图改走文件型剪贴板**（`CF_HDROP` ✓）—— 粘出来是文件而不是位图 ✗，是**行为变化**，需产品决定 ✗；
3. **大图只保存不发剪贴板**，并提示一句 ✓ —— 最保守的方案 ✓。

结论：记录为**已知产品级代价** ✓，不阻塞本次改造 ✓。

## 十、静置（notch 间隔）三档测量

### 10.1 先纠正一个说法：没有"等 N 帧静止"这个参数

§八 里那句"每次推进约等 11.2 帧"描述的是**现象**，不是代码里的旋钮。自动滚动是一个**闭环**：

- 一个 notch 发出后，**不早于 `AUTO_INTERVAL`（现为 60 ms）**才发下一个；
- 这个 notch 由"**在它之后至少一个页面延迟才到达的那一帧**"来判定动没动（`observe`）；
- 连续 `AUTO_IDLE_NOTCHES`（10）个 notch 都没动 ⇒ 自动模式结束。

所以一次采集的耗时 ≈ **notch 数 × max(AUTO_INTERVAL, 页面延迟)**。真机 861 次推进、9 684 帧 ⇒ 约 11.2 帧/次，
其中既有 `AUTO_INTERVAL` 间隔，也有目标窗口自身的滚动动画延迟。

⇒ 真正可调的是**notch 间隔**（`AUTO_INTERVAL`），不是"静置帧数" ✗。本轮已把它做成**仅测量构建可覆盖**
（`test-support` 门控，环境变量 **`SCROLL_AUTO_INTERVAL_MS`**，解析规则：20–5000 ms，非法值回退默认值（现为 60 ms））。
**默认值没有改** ✗。

### 10.2 三档测量步骤

同一页面、同一选区、**同一版本**的 `--release --features test-support` 构建，分别跑一次：

```powershell
cargo build --release --features test-support

$env:SCROLL_AUTO_INTERVAL_MS="200"; .\target\release\snapclip-app.exe
$env:SCROLL_AUTO_INTERVAL_MS="100"; .\target\release\snapclip-app.exe
$env:SCROLL_AUTO_INTERVAL_MS="60"; .\target\release\snapclip-app.exe
```

每档记四项：

1. `[snapclip][scroll] stopped frames=…` 与**你从开始到结束的秒数**；
2. `placements: appended=… contained=… prepended=… unknown=… full=… moved_px=… nonzero=… frames=…`
   —— **重点看四条等式是否仍然成立**：
   `809 + appended × dy == 行数`、`appended × dy + full × dy == moved_px`、
   `appended + full == nonzero`、`appended + full + unknown == frames`；
3. **最终行数是否与基准档一致**（不一致 ⇒ 有位移被跳过 ✗）；
4. **图是否无重复、无缺失横带** ✓。

### 10.3 验收判据（写死，不事后放宽）

某一档只有在**同时**满足下面三条时，才可以考虑设为默认：

- 四条等式仍成立；
- 最终行数与基准档**一致**；
- 图**无重复/缺失横带**。

任何一条不满足 ⇒ **放弃该档**，并把当时的 `placements` 行记进本节。提前步进最危险的后果是踩在滚动动画中途，
位移估计给出错误 `dy` ⇒ **内容错位**（比"慢"严重得多）。
