# 滚动截图拼接器：内存与行数解耦的方案与验证计划

> **本文只陈述事实、待测目标与设计选择，不含实现。** 每条结论都标注了它的性质：
>
> - **[事实]** —— 有代码位置、规范条文或公开文档支撑，可直接核对；
> - **[待测]** —— 目前只是假设或目标，必须由基准测量确认，**不得当作已达成**；
> - **[选择]** —— 我们自己的设计决定，可以改，改了要重新验证。
>
> 上一版把若干推断写成了结论（尤其是把 16.02 ms 的最大帧耗时归因给 `grow()`）。**那一版的相关结论已撤回**，见 §2.2。

---

## 1. 结论摘要

1. **瓶颈归因尚未测量** [待测]。代码里至少有三处会搬动大量数据（`grow()` 的容量翻倍、`Prepended` 的整画布搬移、`band` 覆盖与帧拷贝），**目前没有任何读数能证明 16.02 ms 的基线峰值属于哪一处**。所以第一步不是设计，是**归因测量**（§2.2、§8 阶段 0）。
2. **中间层必须是像素 tile，不是 PNG 块** [选择]。PNG 只能顺序写，这约束的是**最终编码**；中间存储没有理由用 PNG —— 每块都编码会在会话结束时多一轮"逐块解码 + 最终编码"，还要管理块的生命周期与顺序。正确形态是「**可按行读取、可按逻辑顺序前插的像素 tile**」，结束时按最终行序**只编码一次**（§3）。
3. **内存内的 tiled canvas 不带来内存下降** [事实 + 推理]。参考实现 `refer/snow-apps/.../tiled_canvas.rs`（1286 行）证明 tile、首尾追插、行切片、快照回放都可行，但它的 `tiles: VecDeque<Arc<CanvasTile>>` **保留全部像素 tile**（`tiled_canvas.rs:38-43`）⇒ 它解决的是"整图重分配与整图复制"，**不解决常驻内存**。要降内存，必须有「**有限的可改写边缘缓冲 + 已封口 tile 的有界后备存储**」（§3.2）。
4. **`band ≤ view` 推不出窗口正确性** [事实 + 待测]。`band` 是**每次放置**的覆盖幅度；方向反转、连续小步、`prepend` 之后，**内容坐标与缓冲索引都会变**。可改写状态必须用**行的稳定身份或 tile 位置**维护，并用**模型测试**证明（§4）。
5. **内存不是一个数，是四类预算** [选择]。像素规模、工作内存、临时存储、最终文件**各自定义**（§5）。另外：现有的 `Artifact { bytes: Vec<u8> }`（`row_band_png.rs:49`）让**整份编码结果驻留内存** —— 这会让"像素侧达标"仍然端到端超标，属**第三类内存占用者**，必须单独处理（§5.3）。
6. **向上滚动可以实现，靠的是"逻辑顺序可变"，不是 PNG** [事实 + 选择]。PNG 的像素是单个 zlib 流里的顺序扫描行（[PNG 规范](https://www.w3.org/TR/2025/REC-png-3-20250624/)、[libpng](https://man.freebsd.org/cgi/man.cgi?query=libpng&sektion=3)）⇒ 单个文件无法前插 ✗。但**tile 的存放顺序**可以任意调整 ⇒ `Prepended` 只是"把新 tile 插到目录最前"（§3.3）。

## 2. 现状：事实与待测归因

### 2.1 现在这条路径（[事实]，均可对代码核对）

`crates/snapclip-capture/src/scroll/stitch.rs`：

- 画布是**一整块连续 BGRA**：`Stitcher { canvas: Vec<u8>, rows, pos, top: i64, max_rows, view, width }`（`stitch.rs:28-37`）。
- 每帧调用一次 `place(frame, dy)`，结果只有四种：`Appended` / `Prepended` / `Contained` / `Full`（`stitch.rs:16-25`）。
  - **`Appended`**：底部 `grow` 出 `growth` 行，再**覆盖底部 `band` 行**（`stitch.rs:83-103`）；
  - **`Prepended`**：`canvas.copy_within(..known, growth * row)` **把已存在的整块画布整体下移**，再覆盖顶部 `band` 行（`stitch.rs:104-125`）；
  - **`Contained`**：**一个字节都不写**，只移动 `pos`（`stitch.rs:126-129`）；
  - **`Full`**：到上限或扩容失败，**内容不变**（`stitch.rs:20-24`、`stitch.rs:83-91`）。
- `grow()` 用 `try_reserve_exact` + **容量翻倍**，注释自述 "each move copies the whole image"（`stitch.rs:146-158`），失败返回 `false` 而不是 panic ✓。
- 结束时 `Tracker::into_image()` 把**整块画布**交出去（`mod.rs:269`、`scroll_worker.rs:196`），之后才编码。
- 编码产物 `Artifact { bytes: Vec<u8>, rows }`（`row_band_png.rs:49`）—— **整份编码结果在内存里**。

**实测基线**（`tools/codec-bench --scroll`，1280×960 视口、49 帧、29 760 行、release）：

```
拼接 : 中位 1.31 ms / 最大 16.02 ms 每帧 · 画布峰值 161.9 MB · 丢帧 0 · 逐像素正确 true
PNG  : 550 ms · 7.3 MB 峰值 · 3.42 MB 输出
```

### 2.2 三处"搬大量数据"的候选 —— **都还没有读数** [待测]

| 候选 | 代码位置 | 单次搬动规模 | 发生频率 |
| --- | --- | --- | --- |
| **A. `grow()` 容量翻倍 memcpy** | `stitch.rs:146-158` | 整张图（30 000 行时约 152 MB） | 每次会话 O(log n) 次 |
| **B. `Prepended` 整画布 `copy_within`** | `stitch.rs:113` | 已存在的整张图 | **每次向上滚动** |
| **C. `band` 覆盖 + 帧拷贝** | `stitch.rs:97-98`、`stitch.rs:119` | ≤ `band` ≤ `view` 行（1280×960 约 3.7 MB） | 每帧 |
| D. 帧从采集侧拷进画布 | 同上 | ≤ `band` 行 | 每帧 |

**能确定的只有：A 和 B 都会搬动与内容同量级的数据。** 但基线那一次 16.02 ms 到底是 A 还是 B，**目前无法判定** ——
- 该序列里**是否存在 `Prepended`** 取决于合成帧的 dy 序列，文档没有记录；
- `grow()` 是 O(log n) 次、B 是"每次向上一次"，两者的分布完全不同（A 是一次尖峰，B 可能是多次尖峰）。

⇒ 上一版"16 ms 是 `grow()`"的结论**撤回** [待测]。**归因测量必须先做**（§7.1），它直接决定优化目标是"去掉增长"还是"去掉搬移"，两者不是同一个改法。

> **阶段 0 已完成：见 [`docs/35-baseline.md`](35-baseline.md)。** 结论是
> **`grow()` 的重分配就是 16 ms 尖峰**（预分配后纯向下序列的 max 从 16.18 ms 落到 2.04 ms，
> 且最慢帧从"append + 一次 16.4 MB 移动"变成一次 4.1 MB 的 band 覆盖），而
> **`Prepended` 的整画布搬移是 5.74 ms 的第二档**（只有去掉重分配之后才显形：最慢帧是
> prepend、搬 66.2 MB）。两处不是同一个改法，顺序也由此确定：**先去重分配，再去整画布搬移**。

### 2.3 参考实现给出什么、不给什么（[事实]）

`refer/snow-apps/snow-crates/crates/snow-stitch-images/src/tiled_canvas.rs`（1286 行）：

⇒ **但它保留全部 tile** ⇒ 常驻内存随内容增长 ✗ ⇒ **它不是我们要的内存方案**，只是"重分配与整图复制的替代品" ✓

### 2.4 缩略图与上限（[事实]）

- 缩略图已经是增量的：`thumb.refresh(canvas, canvas_rows, top, from, to)` 只遍历脏行区间（`thumb.rs:94`），`fill_preview()` 只读 `thumb.window`，**不碰画布**（`mod.rs:242`）✓ —— 分块后仍需要"尚未落盘的那些行"的像素来喂它（§3.5）。

## 3. 目标架构

### 3.1 数据流（一句话版本）

```
采集帧 ──► 拼接器（只往"边缘缓冲"里写）
              │
              ▼
      边缘缓冲：有限大小，唯一可被改写的地方
              │ 离开"可改写集合"的行 = 已最终
              ▼
      TileStore：原始像素 tile 落临时文件 + 轻量目录（记录逻辑顺序）
              │ prepend 只往目录最前插一条，不搬像素
              ▼（会话结束时，按最终行序）
      装配：逐 tile 逐行读出 ──► 编码器 ──► 最终 PNG（.partial → 改名）
```

三条关键性质 [选择]：

1. **滚动期间不编码** —— 编码只发生一次，且在装配阶段；
2. **滚动期间不搬整图** —— 只有边缘缓冲内部的小范围覆盖；`prepend` 是目录操作；
3. **tile 用原始像素** —— 不用 PNG 块（理由见 §3.2 末），压缩留作后续评估（§9）。

### 3.2 为什么中间层是"像素 tile + 目录"，而不是"PNG 块"

| 方案 | 滚动期编码 | 装配期解码 | 顺序可变 | 结论 |
| --- | --- | --- | --- | --- |
| 边滚边写单个 PNG | 每块一次 | 无 | ❌ | 不支持向上 ✗ |
| **分块 PNG**（上一版方案） | 每块一次 | **逐块一次** | ✓ | 多一轮解码+编码 ✗ |
| **像素 tile + 目录**（本版） | **无** | **无** | ✓（目录可前插） | **编码只一次** ✓ |

⇒ 上一版的"分块 PNG"是把**最终格式的限制**错误地施加到了**中间存储**上 ✗。中间层的唯一要求是"**能按行读、能改顺序**"，PNG 两个都不需要满足。

**代价 [待测]**：raw tile 在临时文件里占 **宽度 × 行数 × 4** 字节 —— 1280×30000 约 **153 MB 磁盘** ✗（现在这个数字是**内存**，方案后变成**磁盘**）。是否可接受必须实测 + 由 §5 的"临时存储预算"约束；不可接受时再评估 tile 压缩 [待测]，**不要一开始就把格式块系统引进来** ✗。

### 3.3 向上滚动：只改目录，不搬像素

- `Appended` ⇒ 目录末尾追加一条 tile 记录；
- **`Prepended` ⇒ 目录最前插入一条** ✓ —— 顺序是逻辑的，与像素存放位置无关 ✓；
- 装配按目录顺序逐行进编码器 ✓ ⇒ 产物是**一个**标准 PNG ✓。

**旁证 [事实]**：公开文档里的成熟工具都只描述向下 —— ShareX 明确"裁掉新截图上半部分、追加到底部"（[ShareX](https://getsharex.com/docs/scrolling-screenshot)），PicPick 的 Scrolling Window 由工具自己向下滚动（[PicPick](https://picpick.app/zh-tw/help/capture/)），Snagit 的滚动区域教程**未能**从公开文档确认向上支持（[Snagit](https://www.techsmith.de/learn/tutorials/snagit/scrollendes-capture)）。**没有找到任何支持向上滚动的工具文档** ⇒ 这条路径**没有外部参考行为**，只能由我们自己的测试证明（§7.2）。

### 3.4 与保存/缩略图的衔接 [选择]

- 会话结束时**母版 PNG 已在盘上**（`.partial` → 改名）⇒ 保存仍走"从 PNG 母版转码"（`apps/snapclip/src/capture/convert.rs`）✓，语义与普通截图一致 ✓；
- `into_image()` 从"交出整块画布"变成"交出**已写好的路径 + 尺寸**"✓；
- 缩略图继续增量，但输入从"画布"变成"边缘缓冲的脏行 + 未落盘 tile"（§3.5）。

### 3.5 缩略图与边缘缓冲的关系 [待测]

缩略图只需要**脏行那段像素**（§2.4）⇒ 每次覆盖 `band` 或封口 tile 时刷新对应区间即可。但如果 tile 一旦落盘就从内存消失，**缩略图必须在那之前刷新完** ⇒ "封口"这一步要保证"该区间的缩略行已经更新" ✓（顺序约束，写进 §4 的 I4）。

## 4. 关键不变量与待证明项

每条都要有**模型测试**（不依赖 Win32、不依赖真实屏幕）覆盖：向下、向上、方向反转、`Contained` 插入、到达行上限、分配失败。

| # | 不变量 | 为什么它不是显然的 |
| --- | --- | --- |
| **I1** | **可改写集合**由"行的稳定身份（或 tile 位置）"维护，**不是** `row < rows - band` ✗ | `rows`/`top` 在 prepend 后整体平移；`band` 是每次放置的覆盖幅度，不是跨 prepend 恒成立的边界。`row < rows - band` 只能当**候选判据**，必须由模型测试验证它在所有方向序列下等价于真实可改写集合 [待测] |
| **I2** | **已封口 tile 永不再写** | 封口判据若错，`band` 重写会打到已落盘内容上 ⇒ 产物错但**测试可能仍然"看起来对"**（只在特定方向序列下错） |
| **I3** | **目录逻辑顺序 == 最终行顺序** | 前插只能前插到"当前内容的顶部"，不能插到已封口内容的中间 ⇒ 前插的边界条件需要证明 |
| **I4** | **进入 tile 之前，缩略图已刷新该区间** | 否则预览缺一块（且不会崩，所以只能靠测试） |
| **I5** | **装配等价于旧路径**：解码后**逐像素相同** + 必要元数据相同（宽高、位深、色彩类型） | **不要求编码流逐字节相同** ✗ —— tile 边界会改变编码器的输入分块，进而改变压缩流；像素等价才是语义 |

**必须声明的一条**：`band ≤ view`（`stitch.rs:132-134`）只能推出"单次放置的覆盖幅度不超过一个视口"，**推不出**"一个大小为 `view` 的窗口足够" ✗。窗口大小（以及"边缘缓冲"的实际容量）必须由 I1 的模型测试**证明**，或由它给出更保守的上界 [待测]。

## 5. 四类预算（分别定义，互不代偿）

### 5.1 预算表

| 预算 | 现在 | 目标 | 由谁保证 |
| --- | --- | --- | --- |
| **B1 像素规模** | `MAX_BYTES`（512 MiB）/ `MAX_SCREENS × view` 约束画布 | **不变** [选择：不把 `MAX_BYTES` 改成"输出文件上限"] | `row_limit`（`mod.rs:80-85`）|
| **B2 工作内存** | 画布峰值 **161.9 MB** | 目标值 [待测]，见 §5.2 | 边缘缓冲 + 编码器 |
| **B3 临时存储** | 0（全在内存） | raw tile ≈ **153 MB 磁盘**（1280×30000）[待测] | TileStore + 清理 |
| **B4 最终文件** | PNG 3.42 MB（同素材） | 不变 | 编码器 |

**`MAX_BYTES` 不做语义转换** ✗：它现在约束的是 **B1**；把它直接当成 B3/B4 的上限会引入一个错误假设 —— **压缩后大小无法由像素数精确预估**（内容决定）。若需要"文件/临时盘上限"，那是**新的**常量与**新的**失败路径 [选择]。

### 5.2 B2 的构成与目标（[待测]）

```
B2 = 边缘缓冲（容量 × width × 4） + 编码器内部缓冲 + 装配时的行缓冲
```

- 边缘缓冲容量**至少**一个视口（960 行 ⇒ 4.9 MB @1280），实际容量由 I1 的模型测试决定；
- 若容量确为 `view`：1280×960 视口 ⇒ 4.9 MB + 编码器 ~7.3 MB ⇒ **约 12 MB**；若封口足够细 ⇒ 可到 **6–8 MB**。
- **这里必须写成目标而不是结论** [待测]：上一版写的"≤ 6 MB"是结构推断 ✗，本版把它改到 §7.2 的验收项里，**阶段 2 实测后才谈达成**。

### 5.3 B2 的第三个占用者：`Artifact { bytes: Vec<u8> }` [事实]

`row_band_png.rs:49` 的 `Artifact` 把**整份编码结果**留在内存里 ⇒ 即使像素侧降到 5 MB，**端到端进程峰值仍会叠加一个完整 PNG**（30 000 行用例是 3.42 MB，四位数尺寸的真实截图可能更高）。

⇒ 如果验收口径是**进程峰值**，导出端必须改成**直接写临时文件**（`.partial` → 改名）而不是先攒 `Vec<u8>` [选择]；如果口径只是"像素侧"，那要在验收里写清**不含导出缓冲** ✗（否则数字没有意义）。

## 6. 背压：三种生产者，三套规则

| 生产者 | 允许丢弃？ | 要求 |
| --- | --- | --- |
| **采集帧** | ✅ 允许丢**尚未处理**的冗余输入帧（滚动是"最新帧优先"，旧帧的价值随新帧到达而下降） | 必须**记录丢帧数量**与**覆盖影响**（丢了哪些区间、产物是否仍有覆盖）✓ |
| **拼接工作** | ❌ 不允许丢 | 队列有界；超过上界 ⇒ **显式失败**并保留可诊断状态 ✓ |
| **封口 tile 持久化** | ❌ **绝不能静默丢** | 内容已经确认进入结果；持久化落后 ⇒ **明确失败**（而不是"慢一点但最终会写完"这种未经证明的保证 ✗）✓ |

**为什么"慢 sink 不掉行"不能当作前提**：帧池的语义决定了"给出帧之后不回收就会被拒绝新帧"这类行为 —— 例如 `Direct3D11CaptureFramePool` 在池满时**停止交付新帧**，而不是无限排队（[Microsoft 文档](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframepool)）。所以持久化必须**主动表达失败**，并由 §7.2 的"慢写"用例证明其行为 ✓。

## 7. 测试与验收

### 7.1 阶段 0：先测基线 + 归因（改任何代码之前）

在**现有实现**上做，不改产品代码：

1. **现有滚动测试 + `codec-bench --scroll`** 全跑一遍，记录：
   - 产物**解码后像素校验值**（不是文件哈希 —— 编码参数变化会让文件变）；
   - **RSS 与峰值额外分配**（两套都记：进程 RSS 与计数分配器）；
   - 每帧耗时的 **p50 / p95 / p99 / max**（现在只有中位与最大）；
   - **`Prepended` 的搬移字节数**与次数（给 `copy_within` 前后加计数即可，仅测量）。
2. **归因实验**（两个变体，各跑同一帧序列）：

## 12. 阶段 2 记录：边缘缓冲 + tile 后备存储（已完成）

### 12.1 做了什么

`crates/snapclip-capture/src/scroll/backed.rs`：`BackedCanvas` 成为产品使用的 store，`MemoryCanvas`
退回测试里的**对照实现**（`#[cfg(test)]`，因为没人运行的实现就是第二份真相）。

| 件 | 形状 |
| --- | --- |
| **后边缘环**（`Ring`） | 固定容量 = 一个视口，`head` 索引，逻辑行 `i` 在物理行 `(head+i) % cap` ⇒ 增长与收缩是下标运算，**不搬像素、不翻倍** |
| **前边缘环** | 同一个 `Ring`，**懒创建**：纯向下会话不分配它（常见情况只占一个视口） |
| **tile 文件** | 只追加的临时文件，目录是 `VecDeque<Tile{offset, rows}>`；`prepend` 只 `push_front` 一条目录项 ⇒ **逻辑顺序可变、像素不动** |
| **`read_rows`** | 让调用方按行取任意区间；`take_all`/装配都走它（跨三个持有者，不可能给出 `&[u8]`） |
| **增量缩略图** | `Thumb::refresh` 多一个 `first` 参数，只喂**脏带 ± 一个缩略行**；`Tracker` 复用一块 scratch，不再每帧分配半个 MB |

**为什么一个视口的环就够**（这次的证明，不再是推断）：一次放置只覆盖**增长边缘的 `band` 行**，而
`band ≤ view`（`stitch.rs` 的 `band()`）；那次覆盖是**纯覆盖**（源是新帧，从不读旧像素）。所以
**离任一边缘超过 `view` 的行永远不会再被写** ⇒ 离开环的行可以封口，环的容量 `view` 足够，而且
封口判据是"它已经离开环"（**不是** `row < rows - band`）。

### 12.2 等价（出口条件）

- `stitch` 的模型测试新增 `the_backed_store_matches_the_oracle_on_every_sequence`：同一批六类序列
  （纯向下 / 纯向上 / 多次反转 / `Contained` / 撞上限 / 分配失败）分别跑 `MemoryCanvas` 与
  `BackedCanvas`，**每一帧**比对 `placement` / `pos` / `top` / `rows` / **像素**，两种 store 完全一致 ✓。
- 为了"同一段代码驱动两种 store"，`CanvasStore` 增加了 `impl CanvasStore for Box<dyn CanvasStore>`
  （转发），模型测试因此不会写成两份。
- `backed` 自己的 `appends_land_in_the_same_place_as_one_buffer`：逐帧比对两个 store 的整幅图像 ✓。
  这条测试在开发中抓到两个真 bug：tile 文件的写偏移没有前进（第二个 tile 覆盖了第一个 ✗）、
  以及增长顺序错误（先 `grow` 再封口 ⇒ 环容量不足时静默少行 ✗）。

### 12.3 读数（`codec-bench --scroll`，1280×960 视口、49 帧、29 760 行、release）

| 指标 | 阶段 0 基线 | **阶段 2** | 变化 |

### 13.3 没做完的部分（如实记录）

**装配峰值没有下降**：`into_image()` 仍然把整图物化成 `Vec<u8>`（**145.3 MB**，§12.3）。

原因不是缺一行代码，而是**导出端口的形状**：`ArtifactWriter::write(&SelectionPixels, …)` 收的是**已经拥有整幅像素**的结构，而 `SelectionPixels` 同时被历史、桌面文件与剪贴板消费。要让装配不再物化整图，需要把端口改成"行带来源"，并回答两个产品问题：

1. **剪贴板**要的是连续 DIB ⇒ 对 30 000 行的长图，那份 145 MB 是**剪贴板本身**的需要，不是装配的浪费；要么接受，要么改成延迟渲染（`WM_RENDERFORMAT`，从文件解码）；
2. **历史/桌面文件**只要文件 ⇒ 可以完全走流式（写 `.partial` → 改名）。

本阶段交付的是**能支撑那条改造的两块料**：按行回放（`for_each_band`，现有测试证明它等于整图）与"存储失败对用户可见"（否则流式导出失败时会退化成一句"已达上限"，比现在更糟）。

### 13.4 下一步（阶段 4 之前必须先做）

1. 端口增加"行带来源"入口（`write_rows` 形态），历史/桌面文件走它 ⇒ 写 `.partial`、成功后改名、失败删除；
2. 剪贴板：先沿用现有整幅路径（**只在需要剪贴板时**物化一份）；延迟渲染列为独立项；
3. 完成后重跑 `--scroll`，报告**装配峰值**（目标：从 145.3 MB 降到"一个带 + 编码器内部"量级，实测为准，不预设数字）；
4. 阶段 4 再把"像素等价 / 峰值 / 每帧 p50 p99 max"变成断言。

## 15. 阶段 3b：文件路径的装配不再物化整图

**做了什么**：`scroll_worker::finish()` 交回一个 `ScrollBands`（持有 tracker，crate 私有），它实现 `BandSource`；`ExportJob` 的像素从一个 `SelectionPixels` 变成一个 `ExportSource`：`Whole` 或 `Bands`。文件写入走 `write_bands`（按 4 MB 带、行带编码、`.partial` 后再提交），**不再先把整幅拼出来**。

**为什么用内部可变性而不是 `&mut ExportJob`**：导出执行器是 `Box<dyn Fn + Send + Sync>`，由 worker 线程通过共享引用调用，拿不到整 job 的独占借用；需要变换的只有"为剪贴板物化一次"这一个动作，所以 `ExportSource` 放在 `Mutex` 里，比重塑执行器形状便宜。

**剪贴板仍是整幅**：一张 30000 行的连续位图天生就要那 145 MB，这是它的价格而不是泄漏；`materialise()` 是唯一物化点，且只被剪贴板调用。

**实测（`codec-bench --bands`，1280×29760）**：

| 路径 | 输出 | 耗时 | 峰值额外分配 |
| --- | ---: | ---: | ---: |
| **带写入（文件路径）** | 0.93 MB | 309 ms | **4.6 MB** |
| 整幅（旧形状，`SelectionPixels` 拥有整图） | 0.93 MB | 324 ms | **154.5 MB** |

⇒ **33.8× 少**，与阶段 3 记的 145.3 MB 对上（差异是编码器与页面共用）。

**证据**：`the_band_source_reproduces_the_whole_image`（逐带回放 == 整图，逐字节）、`a_long_image_reaches_the_writer_as_bands`（长图到达 writer 时是 `write_bands`，且**不会**被当作整幅传进去 —— 整幅入口在该测试里直接 panic）。

## 16. 阶段 4：三条指标进断言，以及那次自证

### 16.1 三条断言与阈值

`cargo run -p codec-bench --release -- --assert` 是门禁入口：**先打印全部读数，再判定**，任何一条不过就以非零退出码结束（所以它能直接放进脚本）。判据写在 `codec-bench` 里，不是文档里：

| # | 断言 | 阈值 | 依据 |
| --- | --- | --- | --- |
| 1 | 产物与页面**逐像素等价** | 三条序列全 `exact` | `down`（整段 30 000 行）、`down up down`、`upward first` —— 最后一条是唯一能进 `Prepended` 的序列 |
| 2 | 带写入峰值 | **< 整幅峰值的 10%** 且 **< 16 MiB 绝对上限** | 实测 3.0%（4.6 MB vs 154.5 MB）；两条同时设是因为只看比值时"整幅也一起变慢变大"会掩盖退化，只看绝对值的则会被进程噪声影响 |

## 17. 决策：封口 tile 的存储

本节把 [`docs/38-tile-storage-alternatives.md`](38-tile-storage-alternatives.md) 的结论并入主方案，**取代** `docs/37` 的压缩容器设计（该文顶部已标注被否决）。

### 17.1 决定：暂不实现压缩（需实测后再定，见 17.6）

维持现状 —— **原始字节 + 临时文件**。理由**不是**"压缩一定超门禁" ✗（那个算式用错了数据，见 §17.6），
而是 **临时磁盘成本还没有被证明构成问题** ✓：

- 实测：一次 1250×38 815 的会话产生约 **190 MB** 临时文件，会话结束即删（§16.6）；磁盘占用随行数线性增长，**与内存无关**；
- 实测：封口量取决于每帧滚动量（`excess`，不是覆盖 band）—— 真机 93 行/帧约 **465 KB/次**，bench 600 行/帧约 **3.07 MB/次**；
  对应 `deflate(level 1)` 约 **1.8 ms** 与 **12.1 ms** ⇒ 压缩成本**随滚动速度变化**，既非"必然超"也不是"必然不超"（§17.6）；
- 要换来的东西（内存）已经从 **161.9 MB 降到 4.0 MB** ✓（§16.5、§16.7），压缩不再有"救内存"的动机；
- 所以现在**不做的原因是收益不明、成本未测** ✓ —— 一旦数据表明磁盘占用不可接受，再按 §17.5 的三条判据评估压缩；
  在拿到实测前，不做任何压缩相关的架构改动 ✓。

### 17.2 三条被否定的路线（不必再试）

| 路线 | 为什么不必再试 |
| --- | --- |
| **CPU 压缩封口 tile** ⏳ **待测** | 17.1 原先据 404 行 band 判定"必然打穿门禁"，但那是**覆盖 band**、**不是封口行数** ✗；封口行数 = `excess`（`backed.rs:557`）。bench 600 行/帧 ⇒ 3.07 MB/次 ⇒ `deflate(level 1)` **12.1 ms**（超门禁 ✗）；真机 93 行/帧 ⇒ 约 465 KB/次 ⇒ 约 **1.8 ms**（在门禁内 ✓）⇒ 取决于滚动速度与内容，必须实测（见 17.6）|
| **mmap 临时文件** ✗ | 文件仍在磁盘 ⇒ **不算"不占临时磁盘"**；且脏页同时占页缓存与物理内存 ⇒ **两边都吃** ✗ |
| **只写最终 PNG、遇向上再补救** ✗ | PNG 是单 zlib 流、只能顺序写 ⇒ 补救只剩"作废重写 / 整段重排 / 放弃已写"三种，都不能接受（双向滚动是硬需求） |

### 17.3 三条待做的便宜改进（未开始 ✗）

- [ ] **封口复用 scratch** —— 现状：`crates/snapclip-capture/src/scroll/backed.rs:391` 每次封口都 `vec![0u8; rows*row]`（2 MB 级分配 ✗）；
- [ ] **合并封口批次、减少 `seek + write_all` 次数** —— **先测实际次数** ✓ 再决定怎么合 ✓；
- [ ] **内存口径固化成"运维口径"一页** —— §16.7 已有四列 ✓，抽成一节并写清每个数字量的是什么 ✓。

### 17.4 长期方向：GPU 常驻 tile（**不进第一版** ✗）

- 1250×38 815 超过单张纹理上限（D3D11 16384）⇒ 切成 **10 张 1250×4096 ≈ 205 MB 显存**；

### 17.5 判据

- 如果将来磁盘占用**真的**成为问题 ⇒ **先走 GPU 常驻**（17.4），**不要**在 CPU 上压缩；
- 任何压缩方案落地前，必须先满足三条：**封口帧 max 不超门禁**（≤8 ms）、**每帧 p95 ≤ 5 ms**、**逐像素等价**。

### 17.6 更正（2026-10-18）：17.1 的算式用错了数据

- 404 行是**覆盖 band**（`stitch.rs:146-148`），**不是每次封口写入 tile 的行数** ✗；
  实际是 `excess = back.rows + growth - view`（`backed.rs:557`）；
- 用 `test-support` 计数实测：**48 次封口 / 49 帧**、每次 **600 行（3.07 MB）**、
  `deflate(level 1)` 花 **12.1 ms**、压缩比只有 **2.4×**（合成高熵页面）；
- 真机 93 行/帧 ⇒ 约 **465 KB/次**、约 **1.8 ms** ⇒ **在 8 ms 门禁之内** ✓；
- ⇒ 所以"必然打穿门禁"不成立 ✗，**17.1 的措辞应读作"待测"** ✓；
- **要测的三样**：① 每次封口的真实字节数（已有计数器 ✓）② 所选编码器在**这台机器**上的压缩耗时（已有 `deflate` 实测方法 ✓）③ **封口帧的 max**（不是平均值 ✗）；
- **在拿到这三项实测之前，不做任何压缩相关的架构改动** ✓；另两条被否决的路线（mmap、只写最终 PNG）与数据无关，仍然成立 ✓。

## 18. 前边缘解封路径的三件事（2026-10-18）

### 18.1 `unseal_front` 的 `offset: 0` 回填：**不可达**，但仍改为真实 offset

容量分支要求 `front.grow_front(rows)` 失败，而 `rows <= need = wanted - front_rows()`、
`need + front_rows() == wanted <= view`，且 `view` 就是环的容量 ⇒ `rows + front_rows() <= cap` 恒成立
⇒ 该分支**不可达**（`Ring::grow_front` 的判据见 `backed.rs`，测试
`the_front_ring_always_has_room_for_what_unsealing_takes` 钉住这个不等式；把判据从 `>` 改成 `>=` 即红）。

即使不可达，它也不能*说谎*：回填现在用**真实 offset**（tile 被截去的那一段从 `tile.offset` 起算），
并保留 `debug_assert!(false, ...)` 作为"这条路径不该发生"的断言 —— 真发生了，行会原样放回，而不是带着 `offset: 0` 混进去。

### 18.2 `middle.order` 非空但 tile 读不回来：谁能造成

| 来源 | 生产可达？ | 依据 |
| --- | --- | --- |
| 测试注入 `break_tile_file` | 仅测试 | 显式删除 |
| 外部删除（杀毒、清理器、用户） | **是** | 文件在 `%TEMP%`，任何进程都能删 |
| 磁盘满 | 否（不会留下不一致的目录） | `ensure_file`/`write_all` 失败 ⇒ `fail()` 且**不** push 目录 |
| `Tiles::drop` | 否 | 只在销毁时删，此时不再有读 |
| 启动清扫 `windows/tile_sweep.rs` | **否** | 在 `begin_scroll_session` 里、`ScrollWorker::start` 之前跑（`overlay/scroll.rs:247` vs `:324`）⇒ 任何 store 都还不存在；且判据要求"别的 pid ∧ ≥1 小时 ∧ 进程已不在"，访问被拒当作活着 |

检出方式：读矩形路径 `read_middle`（上一轮）与**本轮**的 `unseal_front` 都返回 `RowReadError::Missing`，
不再有任何"失败即填零并继续"的静默路径。`grep -rn "fill(0)" scroll/` 现只剩两处：
`backed.rs:490/502`（**本节的容忍路径**，见 18.3）与 `thumb.rs:171`（累加器清零，与错误无关）。

### 18.3 `unseal_front` 改为 `Result`，但**不是**一律拒绝

`unseal_front` 现在返回 `Result<(), RowReadError>`：读不出来时**报错**，同时仍把这批行按零写进前环
（**仅在**它们会被同一步的 band 覆盖时有意义）。`prepend` 拿到 `Err` 后判断：

- 前环仍能满足 `existing` 行（`existing = band - growth`）⇒ **记录并继续** —— 因为这些零值一定被
  `front.write(0, band_src)` 覆盖，图像是完整的；一律拒绝会**丢掉一张本来正确的截图** ✗；
- 前环不够（理论上不可达）⇒ `fail()` ⇒ `prepend` 返回 false ⇒ `Status::Storage` ⇒ 导出以
  `EncodeFailed` 结束、`.partial` 不成为成品。

这条与"一律拒绝"的差别是刻意的：**容忍的前提是被覆盖**，而这个前提由 `existing = band - growth`
的结构保证，并有两测试钉住（`a_prepend_over_a_broken_tile_still_writes_its_band`、
`unsealing_reports_a_broken_tile_instead_of_pretending`）。

## 19. 上限调整、封口故障注入与封口写成本

### 19.1 `MAX_SCREENS` 48 → 100

80 900 行（100 × 809）是新的行数上限，临时磁盘约 **396 MB**，工作内存**仍是约 4 MB**（与行数解耦，§16.6 的实测：38 815 行 = 4.0 MB）。

`MAX_BYTES = 512 MiB` 与它的关系：1250 宽时 80 900 × 1250 × 4 ≈ **404 MB** < 512 MiB ⇒ **行数上限先命中** ✓；对很宽的选区（例如 3840 宽）字节上限约 34 900 行 ⇒ 字节上限兜底 ✓。两个上限的分工用一句话说：**行数管"截多长"，字节管"多宽时能截多长"**。

依赖它的测试全部从 `MAX_SCREENS` 推导（§11 起就是这么写的），因此这次只有两处需要动：`assert_eq!(MAX_SCREENS, 100)`（边界移动的绊线）与 `scroll_format` 里的 JPG/WebP 边界用例（视口尺寸随上限缩小，注释里的算式同步更新）。

### 19.2 `seal-faults`：不填满磁盘也能走满盘路径

`SEAL_FAULT_AT=<n>` 让第 n 次封口按真实写盘失败的**同一条路径**失败：`seal_ring` 拒绝 ⇒ `append`/`prepend` 返回 false ⇒ `Status::Storage` ⇒ 导出以 `EncodeFailed` 结束、**不提交 `.part`**。日志会写明是注入（`injected seal fault at #n`），避免以后被误判为真磁盘故障。

默认构建零影响，有两层证据：

| 检查 | 结果 |
| --- | --- |
| `cargo check -p snapclip-capture --lib`（默认 / `test-support` / `seal-faults` / 两者） | 四种配置均 **0 warning** |
> **更正（证据无效）**：本节曾用"release rlib 里搜 `SEAL_FAULT_AT` 为 0 次"证明门控有效 ✗ —— 但 `[profile.release]` 是 `lto = true` + `strip = true`，rlib 里是 bitcode、字符串字面量不在其中，所以那次搜索什么也没证明 ✗。有效的证据是 **debug rlib** 上的对照表（每种仪器只出现在带它自己特性的构建里、默认构建三项全 0），见 `docs/39` §7.3 ✓。


环境变量只在 feature 打开时读取；解析单独抽成纯函数并用 `#[cfg(feature = "seal-faults")]` 测（测试并行、环境是进程全局，不能直接改环境）。

### 19.3 封口写成本（不压缩，实测）

`codec-bench --scroll`（1280 宽 × 960 视口、每帧 600 px、49 帧）：

| 项 | 实测 |
| --- | ---: |
| 封口次数 / 每次行数 | **48 次 / 600 行** |
| 每次封口字节 | **3.07 MB**（合计 140.6 MB） |
| `seek + write_all` 次数 | **48**（每次封口一次） |
| 单次封口写耗时 **中位** | **596 µs** |
| 单次封口写耗时 **最差** | **1 480 µs** |

换算到真机量级（93 行/帧 ⇒ 每次封口约 **465 KB**）是 **约 0.09 ms/次** —— 这是**换算**，不是实测。

这张表把 §17 的问题说清楚了：**封口本身的写盘是 0.6 ms 量级**，而同一批 3.07 MB 做 level 1 deflate 要 **12.1 ms**（§17.6）⇒ 压缩的成本是它所替代的那次写盘的**约 20 倍**。所以"压缩换磁盘"不是"用一点 CPU 换掉一次昂贵 I/O"，而是"用 20 倍的 CPU 换掉一次本来很便宜的 I/O"。
