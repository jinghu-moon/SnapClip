# 滚动截图拼接器：流式画布方案（只写文档，不改代码）

> 目标：把滚动截图的峰值内存从实测 **161.9 MB** 降到 **≤ 6 MB**（1280×960 视口下理论下限 4.9 MB），并消掉每帧 **16.02 ms** 的 realloc 尖峰。
> 本文只陈述方案与验证，不含实现。所有"事实"都带代码位置。

## 1. 事实（从代码读出，不是推测）

### 1.1 画布怎么长

`crates/snapclip-capture/src/scroll/stitch.rs`：

- 画布是**一整块连续 BGRA**：`Stitcher { canvas: Vec<u8>, rows, pos, top, max_rows }`（`stitch.rs:28-37`）。
- 每帧调用一次 `place(frame, dy)`（`stitch.rs:78`），只有三种结果：
  - **`Appended`**：在**底部**长 `growth` 行，并**重写底部 `band` 行**（`stitch.rs:83-103`）；
  - **`Prepended`**：在**顶部**长 `growth` 行 —— 注意它用 `copy_within(..known, growth*row)` **把整块画布整体下移**，再重写顶部 `band` 行（`stitch.rs:104-125`）；
  - **`Contained`**：画布**一个字节都不写**，只移动 `pos`（`stitch.rs:126-129`）。
- 增长走 `grow()`（`stitch.rs:137` 起的注释与实现）：按需扩容到 `max_rows*row` 上限，**失败返回 `false` 而不是 panic** ✓。

### 1.2 关键前提：旧行会被改写的最大范围 = `band`，而 `band ≤ view`

```rust
fn band(&self, growth: u32) -> u32 {
    (self.view / 2).max(growth + self.view / 4).min(self.view)   // stitch.rs:132-134
}
```

⇒ **每次追加，只有"最后 `band` 行"会被重写，且 `band` 有硬上界 `view`（一个视口高）** ✓
⇒ **`Contained` 帧不改任何旧行** ✓
⇒ **关键补充**：这次重写是**纯覆盖**（`canvas[to-band*row..to].copy_from_slice(&frame[(view-band)*row..])`，`stitch.rs:97-98`）—— 源是**新帧**，**从不读旧画布像素** ✓✓ 所以窗口不需要"为了读旧像素"而多留任何行。
⇒ 并且追加后 `pos = rows - view`（`stitch.rs:99`），可视窗口就是**最后 `view` 行**，而 `band ≤ view` ⇒ **可改写范围永远落在视口之内** ✓✓
⇒ 结论：**窗口 = 恰好 `view` 行**就够了（不需要 `view + band`）✓✓

### 1.2b 16 ms 尖峰的真实成因：**容量翻倍的整块拷贝**

`grow()`（`stitch.rs:146-158`）用 `try_reserve_exact` + **容量翻倍**（`capacity*2`）⇒ 一次会话搬 O(log n) 次，但**每次搬都复制整张图**（注释自己写了 "each move copies the whole image"，`stitch.rs:141-142`）⇒ 到了 30 000 行（约 152 MB）时，一次翻倍就是一次 ~152 MB 的 memcpy ⇒ **实测 16.02 ms 的最大帧耗时正是它** ✓（不是 band 重写 ✓）。

⇒ 换成**固定大小的环形缓冲**（窗口 = `view` 行，分配一次）⇒ **不再有增长、不再有整块拷贝** ✓ ⇒ 尖峰应消失 ✓。

### 1.3 例外：**向上滚动（Prepend）会整体移动画布**

`Prepended` 分支把已存在的所有行 **整体下移**（`copy_within`），并在顶部写新内容。
⇒ 对"边滚边写出文件"的模型，**向上滚动等价于"把新行插到已写内容的**前面**"** ✗ —— PNG 是**只能追加**的流 ✗，这做不到。

这是整个方案**唯一**的架构性限制，必须显式处理（见 §3.1）。

### 1.4 缩略图已经是增量的

`crates/snapclip-capture/src/scroll/thumb.rs`：

- `refresh(canvas, canvas_rows, top, from, to)`（`thumb.rs:94`）只遍历**脏行区间** `[from, to)` 的缩略行（`compute(t, canvas, …)`）；
- `fill_preview()`（`mod.rs:242`）只读 `thumb.window(start, shown)` —— **完全不碰画布** ✓。

⇒ 缩略图只需要"脏行那一段像素"，**不需要整条画布** ✓。

### 1.5 上限与视口绑定

`mod.rs:80-85`：

```rust
fn row_limit(width, view, max_bytes) -> u32 {
    let by_bytes = max_bytes / (width*4);
    let rows = by_bytes.min(MAX_SCREENS * view);   // MAX_SCREENS = 32, MAX_BYTES = 512 MiB
    rows.max(view)
}
```

| 视口高 | 行上限 | 能否到 30 000 |
| --- | --- | --- |
| 800 | 25 600 | ❌ 到不了 |
| 960 | 30 720 | ✓ |
| 938+ | ≥ 30 016 | ✓ |

⇒ **视口 ≥ 938 行**才能支持 30 000 行的页面（这是产品参数，不在本方案范围内改 ✗）。

### 1.6 现在画布怎么变成产物

- `Tracker::into_image() -> (width, rows, Vec<u8>)`（`mod.rs:269`）；
- `scroll_worker.rs:196`：`join().map(Tracker::into_image)` ⇒ **worker 结束时把整块画布交出去**；
- 之后才写 PNG。

⇒ 这正是 161.9 MB 峰值的来源：**整条内容在内存里，直到最后一次性写出** ✗。

### 1.7 实测基线（来自 `tools/codec-bench --scroll`，1280×960 视口 / 49 帧 / 29 760 行）

```
拼接    : 中位 1.31 ms / 最大 16.02 ms 每帧 · 画布峰值 161.9 MB
编码    : PNG 550 ms / 峰值 7.3 MB
端到端  : 88.5 ms 拼接 + 550 ms PNG
```

## 2. 设计：滑动窗口 + 只追加输出

### 2.1 结构

```
                  ┌──────── 窗口（ring，capacity = view 行，分配一次）────────┐
  ... 已最终的行 ──┤ 视口当前显示的行 = 也是唯一可能被改写的行               ├──→ 已最终的行
                  └──────────────────────────────────────────────────────────┘
                                    │
                                    └─ row < rows - band ⇒ 立即交给 RowSink 写出
```

- **窗口容量 = 恰好 `view` 行**（依据 §1.2：`band ≤ view` 且重写是纯覆盖 ⇒ 可改写范围永远在视口内 ✓✓）；
- **行一旦"离开可改写范围"就是最终行** ⇒ 立刻写出（**只追加** ✓），不再留在内存里；
- **`base_row`**：窗口第 0 行对应的内容行号（替代现在"画布第 0 行"的隐含假设）；
- **`Tracker` 的坐标**（`pos`/`rows`/`top`/`image_rows`）改为**内容坐标**，窗口内索引 = `content_row - base_row`；
- **环形使用行**：追加时写进 ring 的空位 ✓，固定容量**永不增长** ✓ ⇒ 消掉 §1.2b 那个 16 ms 尖峰 ✓（现在每次容量翻倍都会整块 memcpy ✗）。

### 2.2 输出的接缝（`RowSink`）

```rust
trait RowSink {                 // 放在 snapclip-capture，注入实现由 shell 提供
    fn push_rows(&mut self, rows: &[u8], row_count: u32) -> Result<(), SinkError>;
    fn finish(&mut self, width: u32, rows: u32) -> Result<(), SinkError>;
    fn abort(&mut self);        // 取消/失败：删半成品
}
```

- 实现由 `apps/snapclip` 提供，**直接复用现有 `PngRowBandSink` 的语义**（逐行带写 ✓，不另造写文件逻辑 ✗）；
- 这就是仓库既有的端口风格：capture 只产出像素行，格式与写盘在 shell ✓（与 `docs/34` 的"capture 给行带、shell 写 sink"一致 ✓）；
- **写盘发生在滚动过程中** ⇒ IO 抖动的风险见 §3.2。

### 2.3 与"保存 = 从 PNG 母版转码"的衔接

- 滚动结束时，**PNG 母版已经在盘上** ✓；
- 保存 = 对该母版**转码**（`apps/snapclip/src/capture/convert.rs`）✓ —— 语义与普通截图完全一致 ✓；
- 于是 `into_image()` 从"交出整块画布"变成"交出已写好的文件路径 + 尺寸" ✓。

### 2.4 缩略图

- 仍然增量：每次写出最终行时，用**那段像素**（还没被覆盖前）调 `thumb.refresh(...)` ✓；
- 参数由 `canvas/rows/top/from/to` 改为 `window_slice/base_row/top/from/to` ✓ —— 机械改动 ✓；
- `fill_preview()` 不变（它本来就只读 `thumb.window` ✓）。

### 2.5 内存核算

| 视口 × 宽 | 窗口容量（= view 行） | 峰值 |
| --- | --- | --- |
| 1280×800 | 800 行 | **4.1 MB** |
| 1280×960 | 960 行 | **4.9 MB** |
| 3840×2160（全屏选区） | 2160 行 | 33.2 MB |

⇒ 1280×960 视口下 **4.9 MB** ✓，落在目标的 5–8 MB 区间内（甚至更好）✓，比现在的 161.9 MB **少 33 倍** ✓✓。

⚠️ **两条必须说清的下限**：
1. **窗口的下限就是"一屏"** —— 视口 2160 行时窗口就是 33 MB，这是"必须持有当前屏幕"的物理下限 ✗，不是设计缺陷；
2. 若将来把 `band` 收小（观感决策 ✗），窗口**不会更小**（窗口 = view 是下界 ✓），只会减少"固定表头被换掉"的影响范围 ✓。

## 3. 前提与风险（每条都写"如果不成立会怎样"）

### 3.1 向上滚动（Prepend）：**本方案不支持**

- **如果不支持**：把 `Prepended` 视为**会话终止条件** ⇒ 停止接收、结束写盘、状态置为新枚举 `Status::UpwardUnsupported`，已写出的行**保留**（用户得到一张顶部可能缺一截、但**内容正确**的图）；
- **替代方案**（都不便宜，留作后续）：
  - 反向模式：先向上滚完再从上往下写 ✗（需要两次经过内容 ✗）；
  - 内存回退：检测到 prepend 就退回整块画布 ✗（峰值回到 161.9 MB ✗，等于方案作废）；
  - 自定义 PNG 分块 ✗（破坏"标准 PNG"这个前提 ✗）。
- **事实依据**：自动滚动（`Auto`）只向下滚 ✓；向上滚动是用户手势 ✓。所以"只支持向下"是可接受的产品约束 ✓，但**必须在 UI 上说清**（否则用户向上滚时会莫名结束 ✗）。

### 3.2 写盘发生在滚动过程中

- **风险**：一次 `write` 卡顿 20–30 ms 就可能掉一帧 ✗（掉帧在滚动里 = 内容缺失 ✗）；
- **缓解**：`RowSink` 实现里做**有界缓冲 + 后台线程**（§4 阶段 1 就把它做成异步的），发送端只在缓冲区满时阻塞；
- **如果缓冲上界不够**：仍然会阻塞 ⇒ 建议缓冲 ≥ 一屏（`view × width × 4` ≈ 4.9 MB）✓。

### 3.3 `MAX_BYTES` 的语义要改

- 现在是"**画布**上限"（512 MiB）✓；流式之后内存与行数**解耦** ⇒ 它变成"**输出**上限"（防磁盘/产物爆炸 ✓）；
- **如果不改**：上限会失去意义（内存早就不吃这么多 ✗，但输出仍可能 1 GB ✗）。

### 3.4 取消与失败

- 沿用现有语义：取消/失败 ⇒ `abort()` ⇒ **删掉半成品文件** ✓（`docs/34 §16` 里 `convert` 已经是"先写 `.partial` 再改名" ✓，此处用同一套 ✓）；
- **风险**：滚动中途崩溃 ⇒ 磁盘上留下 `.partial` ⇒ 启动时清理（与现有 artifact 清理策略一致 ✓）。

### 3.5 逐像素等价不是自动成立的

- 现在"重写 band"的语义是"用最新帧覆盖" ✓；窗口化后**最后一次覆盖必须发生在该行变成最终之前** ✓；
- **如果某行的最后一次覆盖发生在它已写出之后** ⇒ 产物与画布路径不等价 ✗ ⇒ §4 阶段 2 的出口条件就是**逐像素等价** ✓。

## 4. 分阶段落地（每阶段可独立验证）

| 阶段 | 内容 | 出口条件 | 粗估 |
| --- | --- | --- | --- |
| **1** | 引入 `RowSink` 接缝 + **让现有画布路径喂它**（行为不变） | 现有测试全绿 + 产物**逐字节相同** | 1–2 人天 |
| **2** | 环形窗口 + `base_row` + 行最终化 | **与画布路径逐像素等价** + 峰值 ≤ 6 MB（1280×960 视口） | 3–4 人天 |
| **3** | 缩略图改从窗口喂 | 预览与现在逐像素相同 | 1 人天 |
| **4** | bench 断言化（峰值 / 每帧最大耗时 / 像素等价） | 三条指标进 CI（`--scroll` 的断言） | 1 人天 |

**合计：约 6–8 人天**（不含向上滚动支持 ✗，含测试）。

## 5. 验证计划（要能证明"优化了且没改坏"）

1. **逐像素等价**（最重要）
   同一组合成帧序列，分别走"旧画布路径"与"新的流式路径"，产出的 PNG **解码后逐像素相同** ✓；
   装置已有：`codec-bench --scroll` 已经在比"拼接结果 vs 直接生成的完整页面"（当前 `pixel-exact true` ✓），扩展成**两条实现互比**即可 ✓。
2. **峰值内存**
   计数分配器（`codec-bench` 已有 ✓）：目标 **≤ 6 MB**（当前 161.9 MB，理论上限 `view × width × 4` = 4.9 MB + 一成余量）；
   hmm：这条要写清是"encoder 之外、拼接期间的峰值" ✓。
3. **每帧耗时**
   中位与**最大值**：目标**最大 ≤ 4 ms**（当前 16.02 ms）—— 环形窗口消掉整块 `copy_within` 后应显著下降 ✓。
4. **上限行为**
   800 / 960 视口的行数上限不变 ✓；`MAX_SCREENS` 截断行为不变 ✓。
5. **方向限制**
   构造一次"向上滚动"的帧序列 ⇒ 会话按 §3.1 结束、**产物内容正确**、状态可观测 ✓。
6. **取消/失败**
   中途取消 ⇒ **不留半个文件** ✓。
7. **写盘不阻塞**
   用一个"慢 sink"（每次 write 人为延迟 30 ms）跑同一序列 ⇒ **不掉行**（丢帧计数为 0）✓。

## 6. 不做什么

- 不改编码器（`docs/34` 已定稿 ✓）；
- 不改保存面板 / `convert`（它们与画布无关 ✓）；
- 不改视口参数（`MAX_SCREENS` / 938 行门槛是**独立的产品决定** ✓）；
- 不实现向上滚动（见 §3.1 ✓）。

## 7. 未决问题

1. **向上滚动**到底要不要支持？如果要，方案要重做（见 §3.1 的三个替代）✗；
2. **`band` 公式能否收紧**（决定窗口下限、也就是峰值下限）—— 这是观感决策，需要真机看"固定表头被换掉"的容忍度 ✓；
3. **多显示器/DPI 变化**时滚动会话是否允许继续（现有行为未查 ✓）；
4. 写盘线程与 `export_worker` 的关系：复用同一个后台线程池，还是滚动单独一条？✓（建议复用，避免两条取消语义 ✗）。
