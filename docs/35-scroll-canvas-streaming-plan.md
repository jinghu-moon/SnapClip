# 滚动截图拼接器：流式画布 + 分块捕获方案（只写文档，不改代码）

> 目标：把滚动截图的峰值内存从实测 **161.9 MB** 降到 **≤ 6 MB**（1280×960 视口，理论下限 4.9 MB；支持向上滚动时为 ≤ 10 MB，见 §3.1），消掉每帧 **16.02 ms** 的 realloc 尖峰，并**支持向上滚动**。
> 本文只陈述方案与验证，不含实现。所有"事实"都带代码位置或来源链接。

## 0. 结论摘要

1. **滑动窗口成立**（§1.2）：旧行只可能被重写最后 `band` 行，`band ≤ view`，且重写是纯覆盖、从不读旧像素 ⇒ **窗口 = 恰好一个视口高**。
2. **但"边滚边写一个 PNG"不能支持向上滚动**（§3.1）：PNG 的像素是一个 zlib 流里的顺序扫描行，只能从头往后追加，而 `Prepended` 要往**前面**插内容。
3. **改成"块序列 + 最终装配"就支持**（§3.1）：每块一个独立小 PNG，序列可前后插；结束时按顺序逐块解码 → 喂行带编码器 → **一个标准 PNG**。向下滚动走同一条路，只有一条实现。
4. 代价：装配多一遍解码+编码（约 2× 编码时间）、临时块占磁盘 ≈ 成品大小；内存目标不变（一块 + 一窗）。

## 1. 事实（从代码读出，不是推测）

### 1.1 画布怎么长

`crates/snapclip-capture/src/scroll/stitch.rs`：

- 画布是**一整块连续 BGRA**：`Stitcher { canvas: Vec<u8>, rows, pos, top, max_rows }`（`stitch.rs:28-37`）。
- 每帧调用一次 `place(frame, dy)`（`stitch.rs:78`），只有三种结果：
  - **`Appended`**：在**底部**长 `growth` 行，并**重写底部 `band` 行**（`stitch.rs:83-103`）；
  - **`Prepended`**：在**顶部**长 `growth` 行 —— 注意它用 `copy_within(..known, growth*row)` **把整块画布整体下移**，再重写顶部 `band` 行（`stitch.rs:104-125`）；
  - **`Contained`**：画布**一个字节都不写**，只移动 `pos`（`stitch.rs:126-129`）。
- 增长走 `grow()`（`stitch.rs:137` 起的注释与实现）：按需扩容到 `max_rows*row` 上限，**失败返回 `false` 而不是 panic** ✓。

### 1.2 关键前提：旧行会被改写的最大范围 = `band`，而 `band ≤ view`

```rust
fn band(&self, growth: u32) -> u32 {
    (self.view / 2).max(growth + self.view / 4).min(self.view)   // stitch.rs:132-134
}
```

⇒ **每次追加，只有"最后 `band` 行"会被重写，且 `band` 有硬上界 `view`（一个视口高）** ✓
⇒ **`Contained` 帧不改任何旧行** ✓
⇒ **关键补充**：这次重写是**纯覆盖**（`canvas[to-band*row..to].copy_from_slice(&frame[(view-band)*row..])`，`stitch.rs:97-98`）—— 源是**新帧**，**从不读旧画布像素** ✓✓ 所以窗口不需要"为了读旧像素"而多留任何行。
⇒ 并且追加后 `pos = rows - view`（`stitch.rs:99`），可视窗口就是**最后 `view` 行**，而 `band ≤ view` ⇒ **可改写范围永远落在视口之内** ✓✓
⇒ 结论：**窗口 = 恰好 `view` 行**就够了（不需要 `view + band`）✓✓

### 1.2b 16 ms 尖峰的真实成因：**容量翻倍的整块拷贝**

`grow()`（`stitch.rs:146-158`）用 `try_reserve_exact` + **容量翻倍**（`capacity*2`）⇒ 一次会话搬 O(log n) 次，但**每次搬都复制整张图**（注释自己写了 "each move copies the whole image"，`stitch.rs:141-142`）⇒ 到了 30 000 行（约 152 MB）时，一次翻倍就是一次 ~152 MB 的 memcpy ⇒ **实测 16.02 ms 的最大帧耗时正是它** ✓（不是 band 重写 ✓）。

⇒ 换成**固定大小的环形缓冲**（窗口 = `view` 行，分配一次）⇒ **不再有增长、不再有整块拷贝** ✓ ⇒ 尖峰应消失 ✓。

### 1.3 `Prepended` 会整体移动画布 —— 这是架构分叉点

`Prepended` 分支把已存在的所有行 **整体下移**（`copy_within`），并在顶部写新内容。
⇒ 对"边滚边写出一个文件"的模型，**向上滚动等价于"把新行插到已写内容的**前面**"** ✗ —— 单个 PNG 流做不到（§3.1 给出原因与解法）。
⇒ 解法是**改输出模型**（块序列），不是改窗口（见 §3.1）。

### 1.4 缩略图已经是增量的

`crates/snapclip-capture/src/scroll/thumb.rs`：

- `refresh(canvas, canvas_rows, top, from, to)`（`thumb.rs:94`）只遍历**脏行区间** `[from, to)` 的缩略行；
- `fill_preview()`（`mod.rs:242`）只读 `thumb.window(start, shown)` —— **完全不碰画布** ✓。

⇒ 缩略图只需要"脏行那一段像素"，**不需要整条画布** ✓（分块后仍需保留"未落盘块"的像素以供给缩略图，见 §3.1.5）。

### 1.5 上限与视口绑定

`mod.rs:80-85`：

```rust
fn row_limit(width, view, max_bytes: u32) -> u32 {
    let by_bytes = max_bytes / (width*4);
    let rows = by_bytes.min(MAX_SCREENS * view);   // MAX_SCREENS = 32, MAX_BYTES = 512 MiB
    rows.max(view)
}
```

| 视口高 | 行上限 | 能否到 30 000 |
| --- | --- | --- |
| 800 | 25 600 | ❌ 到不了 |
| 960 | 30 720 | ✓ |
| 938+ | ≥ 30 016 | ✓ |

⇒ **视口 ≥ 938 行**才能支持 30 000 行的页面（这是产品参数，不在本方案范围内改 ✗）。

### 1.6 现在画布怎么变成产物

- `Tracker::into_image() -> (width, rows, Vec<u8>)`（`mod.rs:269`）；
- `scroll_worker.rs:196`：`join().map(Tracker::into_image)` ⇒ **worker 结束时把整块画布交出去**；
- 之后才写 PNG。

⇒ 这正是 161.9 MB 峰值的来源：**整条内容在内存里，直到最后一次性写出** ✗。

### 1.7 实测基线（来自 `tools/codec-bench --scroll`，1280×960 视口 / 49 帧 / 29 760 行）

```
拼接    : 中位 1.31 ms / 最大 16.02 ms 每帧 · 画布峰值 161.9 MB
编码    : PNG 550 ms / 峰值 7.3 MB
端到端  : 88.5 ms 拼接 + 550 ms PNG
```

## 2. 设计（一）：滑动窗口，内存与行数解耦

### 2.1 结构

```
                  ┌──────── 窗口（ring，capacity = view 行，分配一次）────────┐
  ... 已最终的行 ──┤ 视口当前显示的行 = 也是唯一可能被改写的行               ├──→ 已最终的行
                  └──────────────────────────────────────────────────────────┘
                                    │
                                    └─ row < rows - band ⇒ 立即交给 ChunkStore 封口
```

- **窗口容量 = 恰好 `view` 行**（依据 §1.2：`band ≤ view` 且重写是纯覆盖 ⇒ 可改写范围永远在视口内 ✓✓）；
- **行一旦"离开可改写范围"就是最终行** ⇒ 可以封口 → 交给块存储（§3.1）✓；不再需要留在内存里 ✓；
- **`base_row`**：窗口第 0 行对应的内容行号（替代现在"画布第 0 行"的隐含假设）；
- **`Tracker` 的坐标**（`pos`/`rows`/`top`/`image_rows`）改为**内容坐标**，窗口内索引 = `content_row - base_row`；
- **环形使用行**：追加时写进 ring 的空位 ✓，固定容量**永不增长** ✓ ⇒ 消掉 §1.2b 那个 16 ms 尖峰 ✓。

### 2.2 输出的接缝：`ChunkStore` + 装配用的 `RowSink`

分块之后有两层"写"：

```rust
/// 一块已经封口、不会再被改写的内容：由 shell 写成独立的小 PNG。
trait ChunkStore {
    /// 把一段最终行压成一块；返回块 id（顺序由存储层记录，允许"插到最前"）。
    fn seal(&mut self, rows: &[u8], row_count: u32) -> Result<ChunkId, SinkError>;
    /// 在序列最前面插入一块（向上滚动）。
    fn prepend(&mut self, rows: &[u8], row_count: u32) -> Result<ChunkId, SinkError>;
    /// 按序列顺序读出所有块（逐行），供装配阶段使用。
    fn replay(&mut self, row: impl FnMut(&[u8], u32) -> Result<(), SinkError>) -> Result<(), SinkError>;
    fn abort(&mut self);   // 取消/失败：删掉所有块与半成品
}
```

- 实现由 `apps/snapclip` 提供；**装配阶段的最终写盘复用现有 `PngRowBandSink`** ✓（逐行带 ✓，不另造写文件逻辑 ✗）；
- 这与仓库既有端口风格一致：capture 只产出像素行，格式与写盘在 shell ✓（`docs/34`）；
- **写盘发生在滚动过程中** ⇒ IO 抖动的风险见 §3.2。

### 2.3 与"保存 = 从 PNG 母版转码"的衔接

- 滚动结束时，**装配产物（PNG 母版）已经在盘上** ✓；
- 保存 = 对该母版**转码**（`apps/snapclip/src/capture/convert.rs`）✓ —— 语义与普通截图完全一致 ✓；
- `into_image()` 从"交出整块画布"变成"交出已写好的文件路径 + 尺寸" ✓。

### 2.4 缩略图

- 仍然增量：每次封口时，用**那段像素**调 `thumb.refresh(...)` ✓；
- 参数由 `canvas/rows/top/from/to` 改为 `window_slice/base_row/top/from/to` ✓ —— 机械改动 ✓；
- **向上滚动后内容行号整体下移** ⇒ 缩略图的 `base` 需要跟着偏移 ✓（见 §3.1.4）；
- `fill_preview()` 不变（只读 `thumb.window` ✓）。

### 2.5 内存核算

| 视口 × 宽 | 窗口（= view 行） | + 当前未封口块 | 峰值（向下） | 峰值（发生向上滚动时，按需回读方案） |
| --- | --- | --- | --- | --- |
| 1280×800 | 800 行 | ≤ 800 行 | **≈ 4.1 + 4.1 = 8.2 MB** | 同左 + 一次块解码 ≈ 1 MB |
| 1280×960 | 960 行 | ≤ 960 行 | **≈ 4.9 + 4.9 = 9.8 MB** | 同左 |
| 3840×2160（全屏选区） | 2160 行 | ≤ 2160 行 | ≈ 33.2 + 33.2 = 66 MB | 同左 |

⚠️ 两条必须说清的下限：

1. **窗口的下限就是"一屏"** —— 视口 2160 行时窗口就是 33 MB，这是"必须持有当前屏幕"的物理下限 ✗，不是设计缺陷；
2. **"当前未封口块"** 是本轮新增的一份像素（未封口的行得留着以便重写 ✓）。若把封口粒度调成"按 `band` 边界"（即每次可改写范围一过就封口 ✓），未封口块就能压到很小 ✓ ⇒ **峰值 ≈ 一窗 + 少量** ✓；下表给的是**保守上界**（整块一屏）✓。

⇒ 1280×960 视口下 **9.8 MB（保守）/ 5–6 MB（细粒度封口）**，比现在的 161.9 MB 少 16–33 倍 ✓✓。

## 3. 设计（二）：分块输出 —— 让向上滚动成为可能

### 3.1 向上滚动（`Prepended`）：**支持**，做法是"块序列 + 最终装配"

#### 3.1.1 为什么"边滚边写一个 PNG"做不到

PNG 的像素数据是**一个 zlib 数据流**里的**顺序扫描行**：`IDAT` 块按顺序拼接后解压出的是"从第 0 行到第 h-1 行"的连续扫描行（[PNG 规范（第三版）](https://www.w3.org/TR/2025/REC-png-3-20250624/)；libpng 的写接口也只有 `png_write_row` / `png_write_rows` 这种顺序写，见 [libpng 手册](https://man.freebsd.org/cgi/man.cgi?query=libpng&sektion=3)）。同一个文件里**无法**在已写内容之前插入行，也无法逆序追加。

⇒ `Prepended`（新内容在**上方**）对一个正在写的 PNG 来说就是"往前面插" ✗ —— 这是**格式限制**，不是我们实现的缺陷 ✓。

**旁证：成熟工具的做法**：ShareX 的滚动截图算法就写成"把新截图的上半部分裁掉、**追加到底部**"（[ShareX 文档](https://getsharex.com/docs/scrolling-screenshot)）⇒ 它的模型天然是**向下、追加**；PicPick 的 "Scrolling Window" 也是由工具自己向下滚动后收集内容（[PicPick 帮助](https://picpick.app/zh-tw/help/capture/)）。两者文档都**只描述向下**，没有向上滚动。

#### 3.1.2 块序列如何成立

把输出从"一个流"改成"**一个块序列**"：

- 每块 = 一段**已最终**的内容行，由 shell 压成**独立的小 PNG**（临时文件）✓；
- `Appended` ⇒ 序列**末尾**追加块 ✓；
- **`Prepended` ⇒ 序列前面插入块** ✓✓ —— 序列是可变顺序的，这正是与"单个流"的本质区别 ✓；
- 结束时**装配**：按序列顺序逐块解码（逐行读）→ 逐行喂 `PngRowBandSink` → **一个标准 PNG** ✓。

产物与"边滚边写"完全等价（同一批行、同样顺序、同一个编码器、同样参数）✓。

#### 3.1.3 块什么时候可以封口（关键不变量）

**一块只有在"它的所有行都已经离开可改写范围"之后才能封口并写盘** ✓，否则向上滚动后的 `band` 重写会打到已封口的内容上 ✗。

判据与 §1.2 相同：内容行号 < `rows - band` ⇒ 最终 ✓。由于 `band ≤ view` ✓，封口只滞后一个视口 ✓。

#### 3.1.4 向上滚动时的重叠从哪来

`Prepended` 的新帧底部要与**已存在内容的顶部**重叠匹配 ✓ ⇒ 需要旧内容的顶部 `view` 行。两种做法：

| 做法 | 内存 | 代价 | 结论 |
| --- | --- | --- | --- |
| **A. 头部窗口**：常驻保留序列开头的 `view` 行 | +一窗（960 视口约 +4.9 MB） | 简单 | 峰值 9.8 MB ✓ |
| **B. 按需回读**：真发生向上滚动时，**解码第一块**取它的顶行 | 不增加常驻内存 | 一次块解码（~26 ms，`docs/34 §16`） | **推荐** ✓（向上是低频路径） |

选 B 时，还要把**缩略图的内容基准**整体下移 `growth` 行（`base_row += growth` ✓），否则预览会错位 ✓。

#### 3.1.5 代价（写清）

1. **装配多一遍解码 + 编码**：30 000 行的编码是 550 ms、逐行解码 26.5 ms ⇒ **装配 ≈ 600 ms，端到端约 2×** ✓（`docs/34 §16`）；
2. **临时块占磁盘 ≈ 成品大小**（块也是压缩过的 PNG ✓，不是 152 MB 的 BGRA ✓）；上限由 `MAX_BYTES` 约束 ✓（§3.3）；
3. **取消/失败要删块** ✓（沿用"删半成品"语义 ✓）；
4. **块数**：按一屏一块算，30 000 行 / 960 ≈ 32 块 ✓（文件句柄不是问题：写完即关 ✓）。

#### 3.1.6 这一条同时统一了向下滚动

块序列对向下滚动同样适用 ⇒ **不需要"向下走流式、向上切模式"两套** ✗ ⇒ **只有一条实现** ✓（这也是选它的主要原因之一）。

### 3.2 写盘发生在滚动过程中

- **风险**：一次 `write` 卡顿 20–30 ms 就可能掉一帧 ✗（掉帧在滚动里 = 内容缺失 ✗）；
- **缓解**：`ChunkStore` 实现里做**有界缓冲 + 后台线程**（§4 阶段 1 就把它做成异步），发送端只在缓冲区满时阻塞；
- **如果缓冲上界不够**：仍然会阻塞 ⇒ 建议缓冲 ≥ 一屏（`view × width × 4` ≈ 4.9 MB）✓。

### 3.3 `MAX_BYTES` 的语义要改

- 现在是"**画布**上限"（512 MiB）✓；分块之后内存与行数**解耦** ⇒ 它变成"**输出**上限"（防磁盘/产物爆炸 ✓）；
- **如果不改**：上限会失去意义（内存早就不吃这么多 ✗，但输出仍可能 1 GB ✗）。

### 3.4 取消与失败

- 沿用现有语义：取消/失败 ⇒ `abort()` ⇒ **删掉所有临时块与半成品** ✓（`docs/34 §16` 的 `.partial` → 改名 语义 ✓）；
- **风险**：滚动中途崩溃 ⇒ 磁盘上留下块目录 ⇒ 启动时清理（与现有 artifact 清理策略一致 ✓）。

### 3.5 逐像素等价不是自动成立的

- 现在"重写 band"的语义是"用最新帧覆盖" ✓；窗口化后**最后一次覆盖必须发生在该行被封口之前** ✓；
- **如果某行的最后一次覆盖发生在它已写出之后** ⇒ 产物与画布路径不等价 ✗ ⇒ §4 阶段 2 的出口条件就是**逐像素等价** ✓。

## 5. 验证计划（要能证明"优化了且没改坏"）

1. **逐像素等价**（最重要）
   同一组合成帧序列，分别走"旧画布路径"与"新的分块路径"，产出的 PNG **解码后逐像素相同** ✓；
   装置已有：`codec-bench --scroll` 已经在比"拼接结果 vs 直接生成的完整页面"（当前 `pixel-exact true` ✓），扩展成**两条实现互比** + 引入真值页面即可 ✓。
2. **向上滚动的专用用例**
   `向下 3 屏 → 向上 1 屏 → 再向下 2 屏` ⇒ 产物与真值**逐像素相同** ✓，且**没有缺行/重行** ✓（这是本方案的核心出口条件 ✓）。
3. **峰值内存**
   计数分配器（`codec-bench` 已有 ✓）：目标 **≤ 10 MB**（1280×960 视口；细粒度封口可到 ≤ 6 MB）；
   **装配阶段**单独报一次峰值（应为"一块 + 编码器"级 ✓）。
4. **每帧耗时**
   中位与**最大值**：目标**最大 ≤ 4 ms**（当前 16.02 ms）—— 环形窗口消掉整块 `copy_within` 后应显著下降 ✓。
5. **上限行为**
   800 / 960 视口的行数上限不变 ✓；`MAX_SCREENS` 截断行为不变 ✓。
6. **取消/失败**
   中途取消 ⇒ **不留块、不留半个文件** ✓。
7. **写盘不阻塞**
   用一个"慢 sink"（每次 write 人为延迟 30 ms）跑同一序列 ⇒ **不掉行**（丢帧计数为 0）✓。
8. **块序列的磁盘占用**
   30 000 行用例的临时块总量 ≈ 成品大小（量出来记录，防止出现"块比成品大很多"✗）。

## 6. 不做什么

- 不改编码器（`docs/34` 已定稿 ✓）；
- 不改保存面板 / `convert`（它们与画布无关 ✓）；
- 不改视口参数（`MAX_SCREENS` / 938 行门槛是**独立的产品决定** ✓）；
- 不做"前置插入到单个 PNG 文件"✗（格式不允许 ✓，见 §3.1.1）。

## 7. 未决问题

1. **封口粒度**：一屏一块 ✓，还是"每次可改写范围一过就封口"（内存更省 ✓ 块更多 ✓）—— 建议后者，阶段 2 用 bench 量块数与峰值后定 ✓；
2. **`band` 公式能否收紧**（决定窗口下限、也就是峰值下限）—— 观感决策，需要真机看"固定表头被换掉"的容忍度 ✓；
3. **多显示器/DPI 变化**时滚动会话是否允许继续（现有行为未查 ✓）；
4. 写盘线程与 `export_worker` 的关系：复用同一个后台线程池，还是滚动单独一条 ✓（建议复用，避免两条取消语义 ✗）；
5. **装配失败的处理**：块都在、装配失败（磁盘满/编码错误）⇒ 保留块让用户重试 ✓，还是删掉 ✓？（建议保留块 + 报错，块本身是有效内容 ✓）。
