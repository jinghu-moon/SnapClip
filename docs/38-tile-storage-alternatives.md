# 38 · 滚动截图封口 tile 的存储：备选方案调研

> 本文是对 `docs/37-compressed-tile-container.md` 的**独立复核**。结论不迁就上一份文档：
> 搜到的事实指向"**第一版不要压缩**"，而 `docs/37` 的核心提案正是压缩。
>
> 标注约定：`[实测]` 本仓库真实数据 · `[来源]` 外部可点链接 · `[估算]` 有算式的推断 · `[待测]` 必须实测才知道。

---

## 0. 结论摘要

**推荐：第一版维持"原始字节 + 临时文件"，只做三处低成本改进，不做压缩。**

| 决策 | 结论 | 依据 |
| --- | --- | --- |
| 封口 tile 是否压缩 | **不做（v1）** | 压缩一次封口要在**捕获线程**上花 ~20 ms（`[实测算式]` 见 §2.2）；挪到后台线程则要引入队列、背压、容器格式、校验和 —— 为一个**已经解决**的问题（4.0 MB 工作集）加四个部件 |
| 临时磁盘 190 MB 是否算问题 | **不算（按当前数据）** | 会话结束即删；用户机器上是 SSD；`[实测]` 一次 38 815 行截图 190 MB、约 45 秒生命周期 |
| 真正值得做的 | ① 封口复用 scratch（现在每次 `vec![0u8; …]`）② 合并封口批次 ③ 把"GPU 常驻"列为长期方向 | ①`[实测代码]` `backed.rs:391` ②③§4、§5 |
| 如果将来一定要压缩 | **deflate（`flate2`+`miniz_oxide`）在后台线程**，不要 LZ4/QOI | LZ4/zstd-1 的比例不足以把 190 MB 压到可忽略（`[估算]` §2.1） |

**一句话**：内存问题已经解决了；再压缩是拿 CPU 和复杂度换一个已经不是瓶颈的磁盘，**收益/代价不成立**。

---

## 1. 现状事实（本仓库，可核对）

`[实测]` 一次真实滚动截图（1250×38 815）的读数，来自 `docs/35 §16.6` 与运行日志：

| 项 | 值 |
| --- | --- |
| 原始像素 | 1250 × 38 815 × 4 ≈ **194 MB** |
| 封口后临时文件 | **190.0 MB** |
| 最终 PNG | **10.8 MB**（≈18× 压缩） |
| 拼接器工作集 | **4.0 MB** |
| 每帧 push（release） | p50 **590 µs** · p95 **1 302 µs** · max **3 634 µs** |
| 导出（含读回 tile） | **1 817 ms** |

**关键**：`4.0 MB` 的工作集意味着**内存目标已经达成**。剩下的 190 MB 是**磁盘**，而磁盘是最便宜的介质。

## 2. 各候选方案的量级（先把"压缩能省多少"算清）

### 2.1 压缩比：不能从最终 PNG 反推 —— 但可以给出区间

用户的纠正 ① 正确：PNG 有自己的**行过滤 + 单一 zlib 流**，与"小 tile 独立压缩"不是同一件事 `[来源: PNG 规范](https://www.w3.org/TR/PNG/)`。

外部证据（**整图**、非 tile）：

| 编码器 | 相对 lodepng 的体积 | 速度 | 许可 / 语言 |
| --- | --- | --- | --- |
| `lodepng`（deflate 级） | 1.00（基准 220.40 MB） | 6.21 MP/s | zlib，C++ |
| `fpng` 单遍 | **1.33×**（293.10 MB） | **110.16 MP/s** | Unlicense，**C++** `[来源](https://github.com/richgel999/fpng)` |
| `qoi` | 1.36×（300.84 MB） | 83.90 MP/s | MIT，C++ `[来源](https://github.com/phoboslab/qoi)` |
| `stb_image_write` | 1.41×（311.41 MB） | 5.76 MP/s | 公共领域 |

⇒ `[估算]` **deflate 级**（lodepng/png crate）的比例最好；QOI/fpng 约 **1.3×** 于它，但**快 15–20 倍**。
⇒ **对 tile 独立压缩**：跨 tile 的相关性丢失 ⇒ 比整图差 **1.2–1.5×** `[估算]` ⇒ 对 194 MB 原始数据，deflate 级可达 **~13–25 MB**、QOI 级可达 **~17–33 MB**。
⇒ 但这些全是 `[估算]`。**必须先测真实 tile 数据**（纠正 ①）。

### 2.2 每帧耗时：这才是否决压缩的原因

`[实测]` 每次封口的行数 = `band = max(view/2, growth + view/4)`（`stitch.rs:146-148`），在 1250 宽、809 行视口下：

```
band ≈ 404 行  ⇒  404 × 1250 × 4 ≈ 2.0 MB / 次封口
```

`[实测算式]` 用外部速度量级：

| 编码器 | 速度（量级） | 压缩 2 MB 需要 | 能否留在捕获线程（max ≤ 8 ms 门禁） |
| --- | --- | --- | --- |
| deflate（`flate2`/`miniz_oxide`） | 50–100 MB/s `[估算]` | **20–40 ms** | ❌ **不行** |
| zstd 级别 1 | 300–500 MB/s `[估算]` | 4–7 ms | ⚠️ 勉强 |
| LZ4 | 1–2 GB/s `[估算]` | 1–2 ms | ✅ 可以 |
| QOI（CPU 编码） | ~85–150 MP/s `[来源]` | 6–12 ms | ⚠️ 勉强 |
| fpng | ~90–115 MP/s `[来源]` | 8–10 ms | ❌ 且是 C++ |

但是封口**不是每帧都发生**：视口 809 行、每帧滚 93 行 ⇒ **约 8–9 帧封一次**。所以：

- **平均**代价可接受（20–40 ms / 9 ≈ 2–4 ms/帧）；
- **但封口那一帧的 max 会变成 20–40 ms** ✗ ⇒ **直接打穿 `--assert` 的 max ≤ 8 ms 门禁**，也会让滚动出现可见卡顿。

⇒ **结论**：deflate 级压缩要放进**后台线程**（捕获线程只做一次 2 MB 拷贝，~0.2 ms）⇒ 于是要引入**线程 + 有界队列 + 背压 + 顺序保证 + 关闭语义**。这就是"为一个非瓶颈问题加四个部件"。

### 2.3 内存 vs 磁盘的口径（回应纠正 ④）

不能一句"128 MB 上限"、一句"总峰值 ≤90 MB"混用。按用户要求拆开（沿用 `docs/35 §16.7` 的四列）：

| 预算 | 现在（原始 + 磁盘） | deflate-in-RAM（后台线程） |
| --- | --- | --- |
| 边缘环 | 4.0 MB `[实测]` | 4.0 MB `[实测]` |
| 压缩缓冲（增） | 0 | +2 MB（一次封口的 scratch）`[估算]` |
| 封口数据常驻 | 0（在磁盘） | **13–25 MB** `[估算]`/`[待测]` |
| 解压回放缓冲 | 0（直接读文件） | +2 MB（复用）`[估算]` |
| **总峰值增量** | **0** | **约 +17–29 MB** |
| 磁盘 | **190 MB** | 0 |

⇒ "≤90 MB"和"128 MB 上限"两个数**不能并列**：前者是**总峰值预算**、后者是**压缩数据的子预算**。若真要做，只能有一个总数（例如 **总峰值 +30 MB**），且必须覆盖上表全部四项（纠正 ④）。

## 3. 存储介质：四条路的对比

| 介质 | 内存 | 磁盘 | 每帧代价 | 覆盖上限 | 复杂度 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| **原始字节 → 临时文件**（现状） | 4.0 MB | 190 MB | p95 1.3 ms `[实测]` | 行数上限 | 已有 | ✅ **v1 保持** |
| 压缩字节 → 内存 | +13–25 MB | **0** | 需后台线程 | 内存预算 | 容器 + 校验 + 线程 + 背压 | ⚠️ 收益不成立 |
| 压缩字节 → 临时文件 | 4.0 MB | 13–25 MB | 同样需后台线程 | 行数上限 | 同上 **+** 仍占磁盘 | ❌ 两份复杂度、一份收益 |
| **mmap 临时文件** | 页缓存占物理内存 `[无来源 · 常识]` | 190 MB | 视页面抖动 | 行数上限 | 低 | ❌ **既不算无磁盘、也可能更费内存** |
| **GPU 常驻 tile** | **~0**（显存 205 MB） | **0** | 只回读 band ≈1 ms | 显存 | 高（新管线） | ⭐ 长期最优，§4 |

### 3.1 关于 mmap 的明确答复

mmap **不算"不占临时磁盘"**：文件仍在磁盘上；而且**写入的脏页会留在页缓存**里，等于同时吃磁盘和物理内存 `[无来源 · 常识，未在本机实测]`。这条可以直接排除。

## 4. GPU 常驻：比压缩更彻底的一条路

`[来源: Microsoft 的 WGC 示例](https://github.com/microsoft/PowerToys/blob/main/src/modules/MeasureTool/MeasureToolCore/ScreenCapturing.cpp)` —— PowerToys 的 MeasureTool 每帧做 `CopyResource` 到 staging 纹理再 `Map`，即**每帧整帧回读**；这印证了"整帧回读是常规做法"，也说明**改为"只回读需要的部分"是可行且更省的**。

可行形态（`[估算]`，未实现）：

- 全分辨率像素**留在 D3D11 纹理**：1250×38 815 无法单张纹理（D3D11 单维上限 16 384）⇒ 切成 `1250×4096` 的 **10 张**纹理，显存约 **205 MB**；
- 捕获线程每帧只需要：**band（~2 MB）**回读用于重写 + **8 个竖条的逐行哈希**用于位移估计（可 `[待测]` 是否能用 GPU 端计算，否则回读约 1/10 的像素）；
- 会话结束**一次性**回读整条（205 MB ≈ 0.1–0.2 s @1–2 GB/s `[估算]`）交给编码器。

⇒ **内存 0、磁盘 0、每帧只回读 2 MB**，理论上比"压缩到内存"更彻底；代价是**新的管线形状**（纹理池、显存预算、设备丢失恢复、驱动差异）。**不是第一版该做的事**，但它是唯一能把"内存和磁盘同时归零"的方案，应作为长期方向记录下来。

## 5. "不压缩，只把有界窗口写进最终 PNG" 是否可行？

用户问的这条，答案是**不可行**（在"必须支持向上滚动"的前提下）：

- PNG 的像素是**单一 zlib 流的顺序扫描行**，不能在已写内容前插入，也无法逆序追加 `[来源: PNG 规范](https://www.w3.org/TR/PNG/)`、`[libpng 手册](https://man.freebsd.org/cgi/man.cgi?query=libpng&sektion=3)`；
- 若"先向下直写、遇到向上再补救"，补救只有三种：**作废重写**（O(N²) 且要保存全部原始数据 ✗）、**整段重排**（等于缓冲全部 ✗）、**放弃已写部分重新开始**（体验不可接受 ✗）；
- ⇒ 只要"双向"是硬需求，**输出顺序必须可变**，就必然有一层"可重排的中间存储"。这一层现在的实现（内存目录 + 临时文件）已经是最小形态。

**旁证**：`[来源: changedetection.io](https://raw.githubusercontent.com/dgtlmoon/changedetection.io/master/changedetectionio/content_fetchers/screenshot_handler.py)` 对超长页面采用"超过阈值就分段拼接"的做法 —— 有些工具干脆**回避**超长输出。我们也可以在产品层选择"**超过上限就分段存成两张**"，但那改变用户可见行为，属于产品决定。

## 6. 对 `docs/37` 的修订建议（按用户五条纠正）

| # | `docs/37` 的问题 | 修订 |
| --- | --- | --- |
| ① | 用"194 MB → 10.8 MB = 18×"**反推** tile 压缩比 | 删除该推导；改为"**必须用真实 tile 数据实测**"，并把 §2.1 的外部区间作为**先验**而非结论 |
| ② | 每帧 +1–2 ms 来自吞吐量推算 | 改为**直接测 p50/p95/p99/max**，且必须覆盖小步滚动与方向反转；并明确"封口帧是 max 的所在" |
| ③ | 索引与尾**每次封口全量追加**（`SNPI`/`SNET`） | **删除**：运行时目录本来就在内存（`VecDeque`），全量追加是 O(N²)；只有"跨进程恢复会话"才需要落盘索引 |
| ④ | 128 MB 上限 与 总峰值 ≤90 MB 并列 | 统一成**一个总峰值预算**，并覆盖：边缘环 + 压缩 scratch + 封口常驻 + 解压回放（见 §2.3） |
| ⑤ | "`crc32fast`/`miniz_oxide` 已在 lock ⇒ 可直接用" | **不成立**：`miniz_oxide` 在 lock 里有 **0.8.9 与 0.9.1 两个版本**，`crc32fast` 是 `png` 的间接依赖；要用必须在 `apps/snapclip/Cargo.toml` 显式声明（并选版本/特性）。`flate2 1.1.10` 依赖 `miniz_oxide 0.9.1` + `crc32fast` |

## 7. 第一版最小方案（推荐）

**保持现状 + 三处低成本改进**（都不引入新依赖）：

1. **封口复用 scratch** `[实测代码]`：`backed.rs:391` 每次封口都 `vec![0u8; rows * row]` ⇒ 换成 `BackedCanvas` 上的一个复用缓冲（2 MB 级，生命周期与会话相同）⇒ 消掉每次封口的分配；
2. **合并封口批次**：现在一次封 `rows` 可能是多次小封口 ⇒ 攒到 ≥ 一个阈值再写，减少 `seek+write` 次数（`[待测]` 实际次数）；
3. **文档口径**：把 `docs/35 §16.7` 的四列预算写进"运维手册"式的段落，避免以后又用错口径。

**明确不做**：压缩、容器格式、尾索引、跨进程恢复、多层 CRC（这些只在"需要跨进程恢复"或"GPU 路线放弃"时才重新评估）。

## 8. 基准计划（若有人坚持要做压缩）

1. **真实 tile 数据**：从一次真机 38 815 行截图里 dump 出 band 大小的 tile（`[待测]`，需要临时 dump 后删除）—— 这是唯一可信的压缩比来源（纠正 ①）；
2. **三种编码器**：deflate(`flate2`)、zstd-1、LZ4 —— 各测 **压缩后字节数** 与 **2 MB 单次压缩耗时**；
3. **每帧分布**：p50 / p95 / p99 / max，**必须含封口帧**（封口帧就是 max 的来源）；
4. **装配**：多一次解压的耗时；
5. **判据（写死）**：总峰值增量 ≤ **+30 MB** 且封口帧 max ≤ **8 ms**（现有门禁）且装配 ≤ **3 s**；任一不满足 ⇒ **放弃压缩**。
