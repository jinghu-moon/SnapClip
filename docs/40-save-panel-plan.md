## 0. 结论摘要

1. **规格把范围定得比"保存面板"大**：它是一张 920 × 569 dip 的模态对话框，含**真实编码预览（编码后再解码）+ 对比滑块**、**尺寸缩放**、**体积上限与自动缩小**、**长截图分割 + PDF**、**每格式高级选项**、**拖出（OLE）**、**Toast/撤销**、**完整校验表**、**UIA 与动效规范**（规格 §2、§4、§5、§6、§9、§10、§16）。**这不是一次能做完的改动**，必须分阶段（§6）。
2. **后端缺的比想象的少、但缺得更关键**：格式能力、偏好结构、转码、行带端口、剪贴板位图都 `[已有]`；真正缺的是**编码服务**（一次编码同时产出"体积 + 字节 + 解码后的预览像素"）、**路径/命名/冲突服务**、**缩放器**、**解码器**、**PDF 写出**、**拖放**、**面板本身**。
3. **"只编码不写盘"其实已经具备** `[已有]`：三个 sink 的 `finish()` 直接返回 `Artifact { bytes }`（内存字节），`convert()` 也接受任意 `impl Write`（`apps/snapclip/src/capture/convert.rs:36-40`）⇒ 体积实测与预览有地基。**上一版把它写成"后端没有"是错的**，已在 §3.3 更正。
4. **有 3 处"规格 vs 本项目已实测结论"的真冲突**，必须先收口再动手（§5.1）：
   - JPG 默认 **4:2:0**（规格 §6.2）vs 本项目实测**文字必须 4:4:4**（`docs/34` §11：文字 PSNR 28.52 → 26.27 dB）；
   - WebP **默认有损**（规格 §6.2 的"无损压缩"默认**关**）vs 后端**只有无损 WebP**（`save_format.rs:142-149`）；
   - 质量档 **92 / 75 / 50**（规格 §12.3 的原型占位）vs 本项目实测最优带 **85–95**（`docs/34` §11）⇒ 75 / 50 未测。
5. **第一个该做的不是 UI，是阶段 1「保存服务」**（路径+模板+序号+冲突+格式+质量 → 文件），纯逻辑、可单测，并让 `convert()` 从死代码变成有生产调用者。
