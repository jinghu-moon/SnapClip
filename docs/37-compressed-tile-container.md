## 触发条件

只有在**同时**满足以下三条时才重新考虑压缩：

1. **临时磁盘被证明是真实约束** —— 例如 `%TEMP%` 所在卷很小、或环境策略禁止临时写入。
   当前**没有证据**：100 屏采集约 400 MB、会话结束即删、随行数线性增长且与内存无关。
2. 且**先**尝试过更便宜的替代：让用户**配置临时目录**（一行配置），或 **GPU 常驻 tile**
   （`docs/35 §17.4`，10 张 1250x4096 纹理约 205 MB 显存，每帧只回读 band）。
3. 且已按 `docs/35 §17.5` 的三条判据**实测通过**：封口帧 max <= 8 ms、每帧 p95 <= 5 ms、逐像素等价。

另记两条已实测的事实，避免后来人重新推导：

- 封口一次写盘约 **0.09 ms**（真机 465 KB 量级：median 596 us、worst 1480 us，每次封口一次 `write_all`），
  而同批数据 level 1 deflate 约 **1.8 ms** ⇒ 压缩约为被替代 I/O 的 **20 倍**成本；
- 高熵内容实测压缩比只有 **2.4x**（不是 18x —— 那个数字来自最终 PNG 的行过滤，不能反推到 tile）。

# 37 · 压缩 tile 容器（已否决的历史方案，未实现）

> 目标：滚动截图的**封口像素**不再落 190 MB 临时磁盘，而是存进一个**压缩的、只追加的、顺序可重排的**容器；
> 同一个容器格式**既能放内存、也能放文件**，将来按预算切换而不换格式。
>
> 相关文档：`docs/35`（流式画布与四类预算、§16.6/§16.7 实测）、`docs/36`（拼接算法、为何旧行只能被重写一个视口）。

## 0. 问题（数字都来自实测）

| 事实 | 值 | 出处 |
| --- | ---: | --- |
| 一次 38 815 行的滚动截图 | **190 MB 临时磁盘** | `docs/35 §16.6` |
| 同一张图的 BGRA 原始体积 | 38 815 × 1250 × 4 ≈ **194 MB** | 算式 |
| 同一张图编码成 PNG | **10.8 MB** | 用户实测 |
| ⇒ 截图内容的压缩比 | **约 18×** | 194 / 10.8 |
| 拼接器工作内存（与行数无关） | **4.0 MB** | `docs/35 §16.6` |

结论：封口像素**不是不可压的** ✓。把它们的**压缩形态**留在内存里，约需 **13–16 MB**
（tile 是独立流，比单流差 1.2–1.5× ✗），只有磁盘方案的 1/12 ✗，却仍比原始数据的 190 MB 少一个数量级 ✓。

## 1. 为什么需要"容器"，而不是散装文件或 PNG 块

现有 `Tiles`（`crates/snapclip-capture/src/scroll/backed.rs:158`）已经是"**一个只追加文件 + 一个 `VecDeque<Tile>` 目录**"，
其中 `Tile` 记 `offset`/`rows`（`:132`）。它已经接近容器，**缺四样东西**：

| 需求 | 散装文件 | PNG 块 | 本容器 |
| --- | --- | --- | --- |
| **只追加**（按到达顺序写） | ✅ | ✅ | ✅ |
| **顺序可重排**（向上滚动时新块插到最前） | ❌ 要靠外部命名/目录约定 | ✅ 用文件名排序 | ✅ **索引导航，payload 不动** |
| **随机按行读**（装配按带回放） | ❌ 每块单独开文件、无跨块索引 | ❌ 每块要解码整个 PNG | ✅ 索引给 offset，按需解一块 |
| **一次完整性校验** | ❌ 每块各自为政 | ⚠️ 依赖 PNG 自身 CRC，但**块内一段坏掉仍可能解出垃圾** | ✅ **每块一个校验和，坏块被检出而不是解出垃圾** |
| 压缩 | ❌ 原始像素 | ✅ | ✅ |

上一轮的实际教训（`docs/35 §16.7`、`docs/36 §10`）：**读失败曾被伪装成成功**，
导出器可能产出带黑洞的成品 ✗。压缩数据更需要"**能检出损坏**"，否则解压出来的是**看似合法的垃圾** ✗——
这比读失败更隐蔽。

## 2. 字节布局

所有整数**小端**。三个区：**头**（固定 32 B）· **记录区**（只追加）· **索引 + 尾**（只追加，每次变更新增一份）。

### 2.1 头部（32 B，文件一次，写完不动）

| 偏移 | 字段 | 类型 | 说明 |
| ---: | --- | --- | --- |
| 0 | `magic` | `[u8;4]` | `"SNPT"` |
| 4 | `version` | `u16` | 目前 `1` |
| 6 | `codec` | `u8` | 默认编码：`0` raw · `1` deflate-fast · `2` deflate-best |
| 7 | `flags` | `u8` | bit0 = 索引位于尾部（本版恒 1） |
| 8 | `row_bytes` | `u32` | 一行的字节数（= `width × 4`） |
| 12 | `width` | `u32` | 像素宽（校验 `row_bytes`） |
| 16 | `tile_max_rows` | `u32` | 单块未压缩上限（`docs` 建议 4 MB ÷ `row_bytes`） |
| 20 | `reserved` | `u32` | 0 |
| 24 | `total_rows` | `u32` | 逻辑总行数（随索引更新；此处只作提示） |
| 28 | `header_crc` | `u32` | 覆盖 0..28 |

### 2.2 块记录（26 B 头 + payload）

| 偏移 | 字段 | 类型 | 说明 |
| ---: | --- | --- | --- |
| 0 | `rows` | `u32` | 本块行数 |
| 4 | `codec` | `u8` | 本块实际编码（可逐块不同 ✓） |
| 5 | `reserved` | `u8` | 0 |
| 6 | `raw_len` | `u32` | 解压后字节数（= `rows × row_bytes`） |
| 10 | `comp_len` | `u32` | payload 字节数 |
| 14 | `payload_crc` | `u32` | **覆盖 payload 存储形态**（压缩后）✓ |
| 18 | `record_crc` | `u32` | 覆盖 0..14 的记录头 ✓ |
| 22 | `reserved2` | `u32` | 0（对齐到 26→ 补齐见下） |
| 26 | `payload` | `[u8]` | `comp_len` 字节 |

> **记录里没有 `first_row`** ✗✓ —— 这是关键设计：**行号属于索引，不属于记录** ✓。
> 向上滚动会让所有行号平移 ✗，若记录自带行号就得改 payload ✗；放进索引则只改索引 ✓。

### 2.3 索引 + 尾（每次封口/重排都**新增**一份，旧的留在原地）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `magic` | `[u8;4]` | `"SNPI"` |
| `tile_count` | `u32` | 条目数 |
| `first_row_offset` ✗ | — | 不需要：第 0 条即逻辑首块 ✓ |
| `entries[tile_count]` | 每条 12 B | `file_offset: u64` + `record_len: u32` |
| `index_crc` | `u32` | 覆盖 magic..entries |

尾部再写 16 B：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `trailer_magic` | `[u8;4]` | `"SNET"` |
| `index_offset` | `u64` | 最新索引的起始偏移（**指向最后一份** ✓） |
| `trailer_crc` | `u32` | 覆盖前 12 B |

⇒ 读取方从文件尾**反向**找最后一个 `SNET` ⇒ 拿 `index_offset` ⇒ 读索引 ⇒ 得到逻辑顺序 ✓。
**永远只追加** ✓，prepend = 写一份新索引（约 12 B × 块数，几十块也就几百字节 ✓）。

### 2.4 十六进制示意（一个双块容器，块 0 raw、块 1 deflate）

```
0000: 53 4e 50 54 01 00 01 01  e8 04 00 00 e8 04 00 00   SNPT............
0010: 04 00 00 00 00 00 00 00  02 00 00 00 9a 3b 00 00   .............;..  ← header
0020: [块0 记录 26 B] 64 00 00 00 00 00 00 03 00 00 00   rows=100 codec=raw
003a: payload = 100 × 1250 × 4 字节原始像素 …
...
xxxx: [块1 记录 26 B] 64 00 00 00 01 00 00 03 00 00 00   rows=100 codec=deflate
...   payload = deflate(100 行)
yyyy: 53 4e 50 49 02 00 00 00  [off0 u64][len0 u32] [off1 u64][len1 u32] crc   SNPI=2 条
zzzz: 53 4e 45 54 [index_offset u64] [crc u32]                              SNET
```

## 3. 编解码候选

| 方案 | 压缩比（对截图） | CPU | 新增依赖 | 备注 |
| --- | --- | --- | --- | --- |
| **raw** | 1× | 0 | 无 ✓ | 兜底（不可压的内容别浪费 CPU）✓ |
| **deflate via `miniz_oxide`（fast）** | 约 12–16× | ~100–200 MB/s | **无** ✓（已在 lock：`miniz_oxide 0.8.9/0.9.1`，`png` 带入） | **推荐默认** ✓ |
| deflate via `miniz_oxide`（best） | 约 18× | ~30–60 MB/s ✗ | 无 ✓ | 可作为"省内存优先"档 |
| `fdeflate 0.3.7`（已在 lock） | 约 8–12× | 很快 ✓ | 无 ✓ | 为 PNG 的滤波后数据优化；对原始 BGRA 比例差些 ✗ |
| zstd / LZ4 | 更好 / 更差 | zstd 中、LZ4 很快 | **要新增** ✗ | 暂不引入 |
| QOI 式 RLE | 约 4–6× ✗ | 极快 ✓ | 自己写 | 比例不够，放弃 ✗ |

**推荐**：`deflate-fast`（`miniz_oxide`，等级 1）✓ —— **零新增依赖** ✓、比例约 12–16× ✓、
CPU 约 100–200 MB/s ⇒ 194 MB 的截图摊到约 1300 帧 ≈ **1–2 ms/帧** ✓（在现有 p95 1.3 ms 之上 ✗，
预计 p95 到 2.5–3.5 ms ✓，仍在门禁 ≤6 ms 之内 ✓）。

## 4. 两种后端，一个格式

```
trait Container {
    fn append(&mut self, bytes: &[u8]) -> Result<u64, ContainerError>;   // 返回 offset
    fn read_at(&mut self, offset: u64, out: &mut [u8]) -> Result<(), ContainerError>;
    fn len(&self) -> u64;
    fn truncate(&mut self, len: u64) -> Result<(), ContainerError>;
}
```

- `MemoryContainer`：一段 `Vec<u8>` ✓（append = `extend_from_slice` ✓）；
- `FileContainer`：只追加的临时文件 ✓（`std::fs::File` ✓，`read_at` 用 `seek` + `read_exact` ✓）；
- **tile 目录常驻内存** ✓（`Vec<ContainerIndex { offset, rows, raw_len, codec }>` ✓，几十条，可忽略 ✓）；
- 与现有代码的关系：这一层**替换** `backed.rs` 里的 `Tiles`（`:158`）✓；
  `CanvasStore`（`store.rs:54`）/ `BandSource`（`ports.rs:130`）/ `replay` / `write_bands` / **错误传播**都不动 ✓ ——
  它们只依赖 `read_rows -> Result<(), RowReadError>` ✓（上一轮已改好 ✓）。

## 5. 预算与上限

| 预算 | 建议值 | 说明 |
| --- | ---: | --- |
| 每块未压缩上限 | **4 MB**（`max_rows = 4MB ÷ row_bytes`，1250 宽 ⇒ 约 838 行/块） | 与现有 4 MB 行带一致 ✓ |
| 内存档总上限 | **128 MB 压缩** | 见下算式 |
| 超限行为 | **拒绝**（`Status::Full` 的兄弟：`Status::Memory`）✗ 或退回落盘 ✓ | 需产品决定（见 §7） |

内存档能装多少行（1250 宽）：每原始字节约 `10.8 MB / 194 MB ≈ 0.056 B`（单流）✓，
tile 独立流按 1.35× ✗ 计 ⇒ `0.075 B / 原始字节` ⇒ 128 MB ÷ 0.075 ≈ **1.7 GB 原始** ≈ **约 340 000 行** ✓
⇒ 在 1250 宽下，**128 MB 压缩内存约等于现在 190 MB 磁盘方案的 9 倍容量** ✓，
远超现有行数上限（`MAX_SCREENS × 视口高` = 48 × 809 ≈ 38 832 行 ✓）。

⇒ 若采用内存档，**"临时磁盘占用"这一项可以清零** ✓，而且**行数上限不再受磁盘约束** ✓。

**先重跑现有门禁，再谈收益** ✓：

1. `cargo run -p codec-bench --release -- --assert`：三条目标（像素等价 / 峰值 / p50·p99·max）✓；
2. 六类序列（纯下 / 纯上 / 多次反转 / `Contained` / 撞上限 / 分配失败）逐帧等价 ✓；
3. `--scroll` 与 `--bands` 重跑对照：**峰值内存**、**每帧 p50/p95/p99/max**、**装配耗时** ✓（这三个数决定"压缩是否值得" ✓）。

**新增故障注入**（补上审查里"剪贴板/短读缺注入"的同族缺口 ✓）：

| 注入 | 期望 |
| --- | --- |
| 把某块 payload 的**一位**改掉 | 校验和失败 ⇒ `RowReadError::Missing` ⇒ `BandSource` 返回 false ⇒ **不产出成品** ✓ |
| 把某块记录头的一位改掉 | `record_crc` 失败 ⇒ 同上 ✓ |
| 索引里某条 offset 指向 payload 中部 | 解压/长度校验失败 ⇒ 同上 ✓ |
| 尾部 `SNET` 被截断 | 找不到最新索引 ⇒ 报错（或回退到上一份索引 ✓ —— 这是只追加索引的额外好处 ✓） |
| 容器被截断到一半 | `read_at` 越界 ⇒ 报错 ✓ |

## 8. 风险与未决

| 风险 | 量级 | 备注 |
| --- | --- | --- |
| **CPU** | 每帧 **+1–2 ms** ✗（fast deflate） | 若改 best 档则 +3–6 ms ✗，可能撞到 ≤6 ms 门禁 ✗ |
| **压缩比损失** | tile 独立流比单流差 **1.2–1.5×** ✗ | 13–16 MB vs 10.8 MB ✓ 可接受 |
| 校验和开销 | CRC-32 约 1–3 GB/s ✓ | 可忽略 ✓（`crc32fast` 是否已在 lock 需确认一次 ✓，否则自己实现或用 `miniz_oxide` 的无校验 API ✗） |
| 内存档在极端页面下的上限 | ≈340 000 行 ✓ | 远超现有行数上限 ✓ |
| 内存档的 OOM 风险 | 压缩块 + 一块解压缓冲 ✓ | 解压缓冲 = 一块（4 MB ✓），不会整图物化 ✓ |

**未决（需产品决定）**：

1. 超限时是**拒绝**（新状态，需 UI 文案，字体是白名单 ✗）还是**静默退回落盘**（无感 ✓ 但行为不可预测 ✗）？
2. 是否需要"**先内存、超限才落盘**"的混合档 ✓（实现上只是两个容器串联 ✓）？
3. 压缩档位是否**暴露给用户** ✗（建议不暴露 ✓，内部按 `codec=1` 固定 ✓）。

## 9. 三个必须先测的数（决定"做不做"）

| 指标 | 现状（实测） | 目标 | 为什么关键 |
| --- | ---: | ---: | --- |
| **峰值内存** | 4.0 MB（working）/ 190 MB（temp） | **≤ 90 MB 总计、temp 归零** ✓ | 这是全部诉求 |
