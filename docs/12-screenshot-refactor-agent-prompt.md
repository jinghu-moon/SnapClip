======================================================================
一、最高优先级原则
======================================================================

1. 根因优先

   发现问题时，先判断它属于实现错误、接口错误、数据结构错误、模块边界错误、调用流程错误还是架构错误。
   如果问题来自架构或边界，必须重构根因，不得在错误抽象外面增加临时判断、兼容层或重复实现。

2. 正确性优先于性能，性能优先于简洁

   优先顺序：正确性 -> 根因解决 -> 性能 -> 架构质量 -> 简洁性 -> 可维护性。
   任何性能优化都必须有基线和修改后数据。禁止凭感觉增加缓存、线程、进程或复杂抽象。

3. 不允许伪完成

   以下情况不得报告为完成：
   - 只修改调用方，未处理根因；
   - 只让一个测试通过；
   - 删除、注释、弱化失败测试；
   - 把人工未验证的功能写成已验收；
   - 留下已知无效旧代码却声称重构完成；
   - 用“后续可以做”替代当前文档要求；
   - 只运行与改动无关的测试；
   - 性能没有实际指标，只做主观判断。

4. 必须持续工作

   除非遇到无法自行解决的外部阻塞，否则不要停留在计划阶段。每完成一个小目标就继续下一个目标，直到当前阶段的质量门禁通过，再进入下一阶段。

5. 不要修改参考项目

   `refer/shot-refer` 只读。允许阅读和总结，不得修改、复制其代码到仓库，也不得把 GDI/WebView/Windows Magnification API 误当成 SnapClip 的 GPU 主路径。

6. 阶段完成必须提交并推送

   每个 Phase 的质量门禁全部通过后，必须立即：

   - 检查 `git status` 和 `git diff`，确认提交中只包含本阶段改动；
   - 创建一个独立、清晰的 commit；
   - 将本阶段对应分支推送到远程仓库；
   - 在阶段报告中记录 commit id、分支名和 push 结果。

   不得把多个阶段的改动攒到最后一次提交。不得提交用户未要求处理的已有改动、密钥、临时日志、构建产物或参考项目修改。推送前必须确认远程分支和当前分支正确；push 失败时保留本地 commit，记录失败原因并继续处理可独立完成的工作，不得强制覆盖远程历史。

7. 允许并行推进，但必须受依赖和文件所有权约束

   可以并行推进互不依赖的阶段或任务，以缩短总工期；不能为了并行而同时修改同一核心文件或绕过阶段契约。并行任务必须：

   - 先声明输入契约、输出接口和负责文件；
   - 使用独立分支或 worktree；
   - 不直接覆盖其他任务的未提交改动；
   - 先完成接口/数据结构约定，再实现各自模块；
   - 合并前分别运行本任务测试，并在集成分支运行全量回归；
   - 发生冲突时由集成任务按根因重新整理，不用简单接受一方版本。

   默认依赖关系：Phase 0 必须先完成。Phase 1、Phase 2、Phase 3 在 Phase 0 的状态、frame、artifact 和错误契约冻结后，可以并行推进各自不共享未冻结接口的任务；如果某个实现依赖另一个阶段尚未稳定的内部接口，则该任务等待接口提交后再开始。Phase 4 可在冻结帧/采样接口稳定后并行；Phase 5 可在渲染层和坐标契约稳定后并行；Phase 6 可在 artifact 和几何契约稳定后并行；Phase 7 必须在相关功能合并后执行。若并行任务修改同一文件，必须拆分为先接口后实现，或改为串行。

======================================================================
三、目标架构不可妥协项
======================================================================

必须最终形成以下边界：

```text
Win32 输入线程
  -> 最新鼠标/选区状态

Capture worker
  -> WGC/DXGI 冻结 GPU texture

Render tick
  -> 静态层、选区层、指针层合成

Export worker
  -> 选区级 GPU readback -> PNG/WIC -> 原子落盘

Application service
  -> artifact -> 可选历史、剪贴板、OCR、低频 Tauri 事件
```

必须遵守：

- 截图框使用 Rust/Win32 原生 HWND，不使用 Tauri WebView 作为全屏像素画布。
- Vue/Tauri 不接收每个鼠标事件、每帧图像或 Base64 像素。
- WGC 首选，DXGI Desktop Duplication 为录屏/增量捕获预留，BitBlt 仅为兼容降级。
- WGC/DXGI 的冻结帧优先留在 D3D11 texture；不能为了统一接口强行转整张 CPU 图片。
- F5 捕获准备不得阻塞 overlay 消息循环。
- `WM_MOUSEMOVE` 不得一对一触发同步 `Present(1)`。
- 确认小选区不得触发整屏 staging/readback。
- overlay 不直接调用剪贴板、SQLite、OCR 或 Tauri AppHandle。
- DirectComposition visual 不得直接绑定任意 `ID3D11Texture2D`；必须由 D2D render target、composition surface 或 swap chain 承载。
- 所有队列、frame ring、采样请求必须有界。

======================================================================
四、执行循环
======================================================================

对每个阶段和每个任务，严格执行以下循环：

### A. 建立基线

修改前运行最相关的测试、构建和人工/运行时探针，记录结果。
性能任务必须记录至少：

- F5 -> monitor ready/provider ready/frame ready/renderer ready/overlay visible；
- 鼠标移动到实际 Present 的 P50/P95；
- 10 秒快速移动的 CPU 平均/P95；
- Private Bytes、Working Set、GPU Dedicated/Shared Memory；
- 选区 readback 字节数和确认峰值内存。

如果暂时无法在当前环境运行某项 Windows 实测，必须明确记录“未执行”和原因，不得假称通过。

### B. 分析调用链

在编辑前确认：

- 谁创建资源；
- 谁拥有资源；
- 谁释放资源；
- 哪个线程调用 API；
- 哪些消息可能被阻塞；
- 哪些数据会跨线程复制；
- 哪些状态可能跨会话残留。

### C. 实施根因修复

使用仓库已有模式和 Windows 原生 API。除非新抽象确实减少复杂度，否则不要增加抽象层。
代码必须保持职责单一：

- domain：纯数据和状态；
- application：用例和编排；
- platform/windows：Win32/WGC/DXGI/D3D11/D2D 适配；
- infrastructure：存储和编码；
- frontend：低频命令、状态和工具栏。

### D. 立即补测试

每完成一组逻辑，马上增加或更新最接近的单元测试、集成测试、GPU 回归或 Windows 探针。
测试必须验证真实预期，不得为了通过而降低断言。

### E. 运行验证

按“最具体 -> 全量”的顺序运行：

1. 修改模块的单元测试；
2. Rust 全量测试；
3. `cargo check --all-targets`；
4. 前端 `npm run typecheck` 和构建；
5. 必要的真实 Windows runtime smoke test；
6. 必要的 WPR/WPA/PresentMon 性能测量。

### F. 阶段报告

每个阶段结束时必须报告：

- 已完成任务编号；
- 修改文件；
- 根因和解决方式；
- 新增测试；
- 执行的命令；
- 关键结果；
- 未完成任务和真实原因；
- 下一阶段入口条件。

只有质量门禁全部通过，才可以进入下一阶段。

======================================================================
五、阶段执行顺序和质量门禁
======================================================================

必须先完成 Phase 0，不得在 P0 架构问题未解决前堆叠依赖其接口的 UI 功能。满足依赖后，可以按照本提示词的并行规则推进多个独立 Phase；每个 Phase 仍必须单独通过质量门禁、提交并推送，不能因为并行而合并验收。

----------------------------------------------------------------------
Phase 0：基线、契约和可观测性
----------------------------------------------------------------------

目标：知道修改前真实行为和资源指标。

任务：

- 运行并保存当前 Rust、前端和构建基线。
- 增加 capture stage timestamps、provider、generation、readback bytes、dirty area 日志。
- 固定 capture event DTO、错误码和状态契约。
- 增加运行时窗口枚举、overlay 健康和热键冲突探针。

质量门禁：

- 现有测试基线可重复；
- 所有未能执行的测试均有明确记录；
- 有一份修改前性能数据；
- 没有修改业务实现来“适应”基线。

阶段交付：

- 通过门禁后提交 Phase 0 commit；
- 推送 Phase 0 分支；
- 记录 commit id、push 结果和基线数据。

----------------------------------------------------------------------
Phase 1：捕获与 overlay 解耦
----------------------------------------------------------------------

目标：F5 捕获准备不阻塞 overlay 消息线程。

任务：

- 实现 CaptureWorker 和容量为 1 的 mailbox。
- `WM_HOTKEY` 只提交 StartRequest。
- 添加 generation，取消和过期结果丢弃。
- WGC 使用 CreateFreeThreaded + FrameArrived/条件等待。
- 保留超时和 BitBlt fallback。
- 设备移除、显示器变化、重复 F5 使用统一取消路径。

质量门禁：

- Preparing 阶段 overlay 仍能响应 Esc/关闭；
- 旧 generation 不会显示到新会话；
- F5 首帧等待不阻塞窗口消息泵；
- WGC 失败能可观测地 fallback；
- 相关测试和全量回归通过。

阶段交付：

- 通过门禁后提交并推送 Phase 1；
- 记录 worker、generation、取消和 fallback 的测试证据。

----------------------------------------------------------------------
Phase 2：渲染节奏和分层
----------------------------------------------------------------------

目标：鼠标输入和 GPU 提交解耦，动态区域不再强迫整屏重绘。

任务：

- WM_MOUSEMOVE 只更新 latest state。
- 使用 WM_APP_RENDER 或刷新 tick 合并输入。
- 一个 tick 最多一次 Present/Commit。
- 构造 Static、Selection、Pointer 三层 visual/surface。
- 去除全屏十字线造成的单包围盒退化；如必须保留，独立动态层处理。
- 增加静态层不变、指针层局部变化的 GPU 回归测试。

质量门禁：

- 鼠标事件不再一对一触发 Present；
- 动态绘制面积可观测并明显小于整屏；
- 选区内原始像素仍逐字节正确；
- 不出现旧会话闪屏、残留选区和拖拽残影。

阶段交付：

- 通过门禁后提交并推送 Phase 2；
- 记录 Present 合并前后的事件数、P50/P95 和 GPU damage 证据。

----------------------------------------------------------------------
Phase 3：选区级 readback 和异步导出
----------------------------------------------------------------------

目标：确认截图只读回用户选择的区域。

任务：

- 实现 GraphicsDevice::read_region(Rect)。
- 使用 CopySubresourceRegion 创建/复用选区 staging texture。
- 正确处理 RowPitch、边界、负显示器坐标和右下角。
- BitBlt 路径直接 CPU crop。
- PNG/WIC 编码移到 ExportWorker。
- 使用临时文件、flush 和 atomic rename。

质量门禁：

- 300x200 选区不产生整屏 readback；
- 4K 大图的 readback bytes 等于选区 staging 尺寸；
- PNG 像素与冻结帧坐标逐像素一致；
- overlay 视觉层不进入 artifact；
- 编码期间 Esc/窗口消息不被阻塞。

阶段交付：

- 通过门禁后提交并推送 Phase 3；
- 记录不同选区尺寸的实际 readback bytes 和峰值内存。

----------------------------------------------------------------------
Phase 4：放大镜和低阻塞取色
----------------------------------------------------------------------

目标：完成 docs/Temp/放大镜设计.md 的 GPU 放大镜重构。

任务：

- 统一 15x15/21x21 source rect、32x32 tile 和中心像素计算。
- 实现 nearest-neighbor、倍率、网格、中心实心圆/高亮框。
- 实现颜色 swatch、Hex、物理坐标。
- 实现边缘翻转、work area 钳制和不遮挡鼠标热点。
- 实现三缓冲 staging + non-blocking Map/DO_NOT_WAIT。
- 颜色采样最多 60Hz；tile 命中时不重复提交。
- 采样不经过 Tauri，不创建常驻线程。

质量门禁：

- 放大镜源区域边缘仍固定尺寸；
- 一个源像素对应一个放大单元；
- grid >= 4x 才显示；
- 中心标记不再出现误导性的黄色小点；
- Hex 读取不会阻塞鼠标或 GPU Present；
- 黑/白/彩色背景和高 DPI 视觉回归通过。

阶段交付：

- 通过门禁后提交并推送 Phase 4；
- 记录放大镜视觉回归、采样队列上限和 Hex stale 行为。

----------------------------------------------------------------------
Phase 5：工具栏和对象化标注
----------------------------------------------------------------------

目标：标注可抗锯齿、可调整、可撤销并可再次编辑。

任务：

- 实现 AnnotationDocument、AnnotationItem、AnnotationStyle、undo/redo。
- 支持选择、移动、缩放、删除、复制、置顶/置底。

- 屏幕预览和导出重放同一文档。
- 当前对象使用旧/新 bounds 并集进行局部更新。
- 工具栏使用低频 Tauri 命令，不进入像素管线。

质量门禁：

- 多个标注互不破坏；
- 样式修改只影响选中对象；
- 一次拖动只产生一个 undo step；
- 标注控制点、工具栏不进入 artifact；
- 预览和导出视觉一致；
- 抗锯齿和 100/125/150/200% DPI 回归通过。

阶段交付：

- 通过门禁后提交并推送 Phase 5；
- 记录标注对象模型、undo/redo 和预览/导出一致性测试。

----------------------------------------------------------------------
Phase 6：垂直和水平长截图
----------------------------------------------------------------------

目标：可靠拼接，无重复、无空白、可解释失败。

任务：

- 抽象 StitchAxis，垂直/水平共享匹配核心。

- 使用 position/max_depth 防止来回滚动重复扩张。
- 重叠区域由新帧覆盖；低置信度帧拒绝。
- 处理 sticky header/footer，连续无增长才终止。
- UI 显示方向、进度、置信度、停止原因。

质量门禁：

- 垂直和水平合成帧测试都通过；
- 动态内容不会生成错误 shift；
- 失败不会伪装成空白或完整图；
- 最大尺寸、用户取消、到底和匹配失败均有确定结果；
- frame mailbox 有界。

阶段交付：

- 通过门禁后提交并推送 Phase 6；
- 记录垂直和水平拼接黄金测试、失败原因和输出尺寸。

----------------------------------------------------------------------

目标：把 artifact 安全接入历史、剪贴板和 OCR，并完成最终验收。

- 重跑全量测试、前端检查、安装包构建。
- 使用 WPA/WPR、PresentMon 和进程计数器完成前后性能对比。

质量门禁：

- 所有适用清单项均已勾选并有证据；
- 没有遗留已知无效实现、重复实现或过渡兼容层；

阶段交付：

- 通过门禁后提交并推送 Phase 7；
- 记录最终集成 commit、远程 push 结果、完整测试和性能对比。

======================================================================
六、代码修改规范
======================================================================

1. 先读后改

   改核心代码前必须读取调用方、被调用方、相关测试、配置和模块说明。

2. 小步但不追求最小 diff

   可以进行大规模合理重构；不要为了 diff 小而保留错误架构。

3. 使用 apply_patch 修改文件

   不使用 shell 重定向、临时 Python 脚本或破坏性 git 命令覆盖用户文件。

4. 不回滚用户改动

   工作区可能有未提交修改。只处理本任务相关文件，不得使用 `git reset --hard` 或 `git checkout --`。

5. Rust/Windows 资源管理

   明确每个 COM、HWND、D3D11 texture、staging、frame pool、swap chain 的 owner、线程和 Drop 顺序。
   设备移除和窗口销毁必须可重复清理。

6. 性能代码禁止隐式分配

   鼠标移动、render tick、取色和录屏路径避免创建整屏 Vec、整屏 Bitmap、Base64 和无界任务。
   如存在必要分配，必须记录大小、频率和上限。

7. 不在 hot path 打日志洪水

   允许阶段日志和采样统计；鼠标移动日志必须节流或仅在诊断模式启用。

======================================================================
八、阻塞处理规则
======================================================================

遇到失败时：

1. 先保留失败现场和完整错误；
2. 判断是代码、环境、驱动、权限、API 能力还是测试假设问题；
3. 尝试至少三种合理的本地排查路径；
4. 不得直接关闭功能、跳过测试或写永久 fallback 掩盖问题；
5. 如果确实需要用户手工操作，只请求最小必要信息，并明确提供复现步骤；
6. 在阶段报告中写清“阻塞原因、已尝试路径、下一步和未验收风险”。

只有在同一阻塞条件连续三次无法推进且确实需要外部状态变化时，才能将该项标记为 blocked；不能因为任务复杂就提前停止。
