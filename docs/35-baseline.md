# 滚动截图拼接器：阶段 0 的归因与基线

> 对应 `docs/35-scroll-canvas-streaming-plan.md` 的 §7.1 / §8 阶段 0。
> **本轮不改任何产品行为**：测量代码全部在 `test-support` 特性下，默认构建的 `stitch.rs`
> 没有计数器、没有时钟读取、没有多余字段（`cargo check -p snapclip-capture` 无告警即证）。

> 检出后执行 `cargo run -p codec-bench --release -- --attribution`；`docs/35` §12 记着
> 阶段 2 之后的同一组读数。

## 1. 测了什么

三个候选（`docs/35 §2.2`）各记"搬移字节 / 耗时 / 次数"：

| 候选 | 代码位置 | 计数方式 |
| --- | --- | --- |
| **A** `grow()` 容量翻倍的重分配 | `stitch.rs` 的 `grow` 调用点（`grow_to`） | 调用前后 `as_ptr()` 变了才算一次移动；字节数 = 移动前画布长度 |
| **B** `Prepended` 的整画布下移 | `stitch.rs` 的 `copy_within` | 字节数 = 已知画布长度 |
| **C** `band` 覆盖 + 帧拷贝 | `stitch.rs` 两处 `copy_from_slice` | 字节数 = `band × 行宽` |

每次 `push` 还记录**这一帧各自搬了多少**，因此最慢那一帧可以直接归因，不必推测。

## 2. 四个配置（2×2）

- 第一轴：**纯向下** vs **下滚后向上越过起点**（只有后者能进 `Prepended`）；
- 第二轴：**默认画布** vs **画布预先分配到行上限**（后者按构造不会重分配）。

> 一个中间发现：下滚若干屏后再向上滚，画布已经比视口高 ⇒ 那是 `Contained`，**不是**
> `Prepended` ✗。`Prepended` 只在"视口回到会话起始帧之上"时发生，所以混合序列必须**从页面
> 中间开始**（本测量从第 8 个步长处开始，下滚 20 步、上滚 22 步，其中 2 步越过起点）。

## 4. 归因结论

1. **16 ms 的尖峰来自 `grow()` 的重分配** ✅ —— 把画布一次性预分配后，纯向下与混合两种序列
   的 max 都从 ~16 ms 落到 **1.7–2.0 ms**，而且最慢帧从"append + 一次 16.4 MB 移动"变成了
   一次 4.1 MB 的 band 覆盖。**这不是从结构推断，是同一帧内的字节数直接对上的。**
2. **`Prepended` 的整画布搬移是第二个成本，且被前一个掩盖** ✅ —— 只有去掉重分配之后它才显形：
   混合序列的 max 变成 **5.74 ms**，最慢帧是 prepend、搬了 **66.2 MB**。它占帧数是
   `p99 = 5.74` 而 `p95 = 1.52`，即**不到 5% 的帧**触发，但每次都是一次整画布搬移。
3. **band 覆盖是常数成本** ✅ —— 每帧 4.1 MB，`band` 随 growth 变化但不超过一个视口，
   在所有配置里都不是尖峰。
4. **`grow` 的搬移总量很小但很尖** ✅ —— 全程 5 次、共 52.7 MB（O(log n) 的证据），
   与"每次会话移动 O(log n) 次"的注释一致；问题从来不是总量，是**单次 16.4 MB 落在某一帧上**。

⇒ 对方案的直接影响：**阶段 1/2 的目标可以同时写死** —— 去掉重分配（预分配或固定容量缓冲）
消掉 16 ms；去掉整画布搬移（tile 目录前插）消掉 5.7 ms 那一档。两者不是同一个改法，
优先级也明确了：**先重分配，后搬移**。

## 5. 四类预算的当前值（`docs/35 §5.1`）

| 预算 | 当前实测 | 说明 |
| --- | ---: | --- |
| **B1 像素规模** | 29 760 行（上限 30 720 行 = `MAX_SCREENS × 960`） | 画布峰值 **161.9 MB** |
| **B2 工作内存** | **161.9 MB**（画布）+ 7.3 MB（PNG 编码器）≈ **169 MB** | 编码器数字来自 `docs/34 §16` |
| **B3 临时存储** | **0** | 还没有后备存储 |
| **B4 最终文件** | **3.42 MB**（PNG，同一素材） | `docs/34 §16` |

**RSS 峰值的构成**：四次运行的 RSS 峰值都是 **316.5 MB** ≈ 153 MB（合成页面本身）+ 161.9 MB
（画布）。也就是说这张表里的 RSS **包含测量素材**，不能直接和产品的进程峰值比较 ✗；比较
"优化前后"时，四条运行的素材相同，所以**差值**仍然有效 ✅。

**RSS 现在 vs 峰值**：纯向下跑完后 RSS 仍是 306.7 MB ⇒ 画布交出去并 drop 之后，分配器/系统
并没有把内存还给 OS。这不是泄漏（同一进程后续运行没有继续增长），但说明"峰值"是评价内存时
更诚实的口径 ✅。

## 6. 这一轮没有测的

- **真实屏幕内容**：合成页面是高熵纹理，绝对耗时与真实网页不同（与 `docs/34 §12` 同一个限制）；
- **多显示器 / DPI 变化**（`docs/35 §9.7` 仍未查）；
- **缩略图**耗时由 `--scroll` 单独报（本表已扣除，`thumb` 不在归因范围内）；
- **内存不足**与**取消**路径（属阶段 1 之后的失败用例）。
